# Кампания recall >=90%, precision >=60%

**Выполняется, итоговые метрики пока не объявлены.** Это реальные обучения и
точный подбор порогов; фаворит сохранён отдельно в [favorite.json](favorite.json).
Новые веса не активируются в API или политике выдачи.

## Объём и учёт результатов

1. 480 записей основной сетки: окно ×давность ×баланс ×признаки. На основном
   fold это 384 разных обучения: вся история и окно 10 лет совпадают. Повторные
   записи ссылаются на тот же результат, без фиктивного повторного обучения.
2. До 12 родителей, по 4 на каждый набор признаков, ×30 условных уточнений.
3. 168 сравнений других семейств: LR 24, RF 24, LightGBM 60, XGBoost 60.
4. 24 продолжения обучения со старым replay. Checkpoint обучен на разрешённых
   данных кампании, а не на потенциально будущих метках пакета-фаворита.
5. 10 лучших cold-fit конфигураций ×3 seeds ×3 исторических folds, с повторным
   использованием точных совпадений. Warm-start здесь не переносится на ранние
   folds вместе с более поздним checkpoint.
6. None/isotonic-калибровка 10 финалистов в дополнение к уже выполненной sigmoid;
   до 25 ансамблей на основном fold и их доступные A/C-проверки.

Объект выбора — модель и её собственный порог. Цель: максимум F1 при одновременных
precision >=0.60 и recall >=0.90 на отдельной выборке подбора. При отсутствии
решения `optimal=null`; отдельно сохраняются полные точки максимума recall при
precision >=60%, максимума precision при recall >=90% и свободного максимума F1.

Основная диагностическая точка при отсутствии допустимого порога — максимум
precision при recall >=90% на threshold-когорте. При ранжировании на validation
сначала идут выполняющие оба ограничения, по F1. Среди невыполняющих — меньший
относительный дефицит худшего ограничения, затем F1. Это критерий близости к цели,
а не заявление, что кандидат имеет самый высокий свободный F1.

Все precision/F1/recall считаются при одном пороге, без средних по порогам/folds.
Порог сохраняется до оценки validation-меток; на validation его не перенастраивают.
Seed=42 остаётся основным; удачный seed из robustness не выбирается задним числом.

## Явная корректировка временной схемы

Исходное предложение с ежегодной доступностью исходов оказалось непригодно:
в fold B оставалось 2 списания для порога, в fold C — 0 для калибровки.
Исполняемый [protocol.json](protocol.json) задаёт паузу на созревание исходов и
общую дату моделируемого обучения до начала validation FY.

| Fold | Fit до FY | Early | Calibration | Threshold | Validation | Списаний для порога |
|---|---:|---:|---:|---:|---:|---:|
| A | 2015 | 2016 | 2017 | 2018 | 2021 | 574 |
| B | 2017 | 2018 | 2019 | 2020 | 2023 | 163 |
| C | 2018 | 2019 | 2020 | 2021 | 2024 | 185 |

В каждый development-компонент входят только исходы, известные до начала его
validation FY. Периоды выдач различных ролей не пересекаются. Это историческая
проверка выборки завершённых кредитов: selection bias остаётся. Использование
срока — исследовательская ветка до подтверждения его доступности при заявке.
FY2024–2026 не называются новым независимым тестом; ранее эти данные уже изучались.

## Нагрузка и продолжение запуска

По просьбе пользователя одновременно выполняются **2 обучения ×2 потока**, с nice=10.
Dispatcher поддерживает живой лимит `maxActiveFits` в локальном
`scoring_training/runs/recall90-precision60-campaign-v1/concurrency.json`.
Pool допускает максимум 3 workers, но передаёт им не более указанного числа задач.
Менять control-файл следует атомарной заменой; при снижении текущие fits завершаются,
новые задачи ожидают свободного лимита. Полный план от снижения скорости не сокращается.

Среда — macOS ARM64, CatBoost обнаружил **0 CUDA-устройств**. В [официальной
таблице CatBoost](https://catboost.ai/docs/en/installation/python-installation-method-pip-install?lang=en)
GPU на macOS не поддерживается. Пользователь выбрал продолжение локально на CPU.

CPU-конкуренты закреплены в `scoring_training/requirements-campaign.txt` и установлены
с `--no-deps`, чтобы не менять версии исходного inference-пакета. На этом Mac нет
отдельного Homebrew libomp. Уже установленный runtime из scikit-learn подключён
жёсткой ссылкой в lib-каталог используемого Python, без перезаписи существующих
файлов. Это сохраняет один физический OpenMP runtime и работает независимо от
`DYLD_LIBRARY_PATH`, который macOS очищает при запуске защищённого nice.
Блокирующая Homebrew лицензия Xcode не принималась. Подробности — [runtime.json](runtime.json).

Из `fastapi/`, для продолжения после остановки:

```sh
MPLCONFIGDIR=/tmp/alpha-scoring-mpl \
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 MKL_NUM_THREADS=2 \
nice -n 10 scoring_training/.venv/bin/python -m scoring_training.campaign \
  --stage all --workers 3
```

Не запускать второй dispatcher одновременно. Готовые точные совпадения берутся из
проверенного журнала; незавершённые записи пересчитываются. Результаты отдельного
обучения содержат хеши кода/модели, полный config, selection и фиксированные метрики.
Коммиты делаются по завершённым этапам, не по комбинациям; push не выполняется.
Внутри sandbox nice может быть запрещён: фактический приоритет текущей кампании
отдельно установлен и проверен как 10. Не считать одно наличие nice в команде
подтверждением пониженного приоритета при сообщении Operation not permitted.

## Где находятся результаты

Локальный игнорируемый каталог:
`fastapi/scoring_training/runs/recall90-precision60-campaign-v1/`.

- `progress.json`, `journal.jsonl`, `campaign-console.log`: текущая стадия и прогресс.
- `stages/*-configs.json` / `*-results.json`: полный состав и результат каждого этапа.
- `trials/<id>/`: модель, точный выбор порога, все рабочие точки, raw/probability
  предсказания для воспроизведения, явные ошибки и предупреждения.

После завершения сюда экспортируются `trials.csv`, `operating-points.csv`,
`top10.csv/json`, `leaders.json`, `summary.json`, `fixed-future-diagnostics.json` и график. Пустой
optimal в выгрузке означает отсутствие решения под оба ограничения. Метки/строки
кредитов и все пробные веса остаются локальными; Git получает агрегированные результаты.

## Топ-10 и разрешённая очистка

По просьбе пользователя выбираются до 10 разных улучшений относительно фаворита
на той же FY2023-когорте. Сначала выполняющие обе цели, затем F1, recall, precision;
при равенстве предпочтительнее безопасные признаки и калиброванная вероятность.
Одинаковые бинарные решения на тех же кредитах не занимают несколько мест.
Рост F1 с recall не ниже фаворита допускается с явным указанием обмена precision.
Если улучшений окажется меньше десяти, число не дополняется скрыто худшими вариантами.

Для каждого top-кандидата выполняются фиксированные дополнительные проверки на
FY2024/2025/2026 и повторное предсказание из сохранённого артефакта. Только после
совпадения вероятностей и TP/FP/FN/TN удаляются остальные пробные model.joblib и
ненужные predictions.npz. Топ-10, компоненты ансамблей и оба экземпляра фаворита
сохраняются. Все агрегированные метрики, параметры и конфигурации остаются в журнале;
`retention.json` содержит проверенные SHA-256 и объём очистки. Это явное разрешение
пользователя, а не автоматическое удаление во время ещё незавершённой программы.

Снимки завершённых этапов коммитятся отдельным stage-committer. Он использует
приватный Git index, чтобы не включить чужие staged/unstaged изменения; обновляет
только собственную строку общего индекса отчётов. Наблюдение в этом чате проверяет
прогресс раз в 30 минут и сообщает только новые улучшения, завершение или проблему.
