# Пороги списания: максимум F1 и приоритет recall

Перебраны **41 892 порога** текущей `sba-scoring-v1` без переобучения. Приоритет
выявления списаний требует снижать порог и принимать рост ложных срабатываний.
Максимум F1 сам по себе не обеспечивает высокий recall на поздних когортах.

Для сценария с акцентом на recall выделен **экспериментальный кандидат
`p >= 0.054874051193982705`**: лучший F1 среди порогов с recall >=95% на FY2017.
На FY2018–2019 он выявляет **5 470 из 5 927 списаний (92,29%)**, пропуская 457.
На FY2020–2026 recall снижается до **65,97%**; такой порог нельзя считать
подтверждённым решением для выявления 95% будущих списаний.

## Методика и границы оценки

- Цель: `LoanStatus=1`, кредит списан; считаются кредиты, а не сумма потерь.
- Положительный прогноз: калиброванная вероятность **`p >= threshold`**. Точный
  порог хранится в JSON; округление для отображения не является новым порогом.
- CatBoost обучен на FY2010–2016; модель и sigmoid-калибратор не изменялись.
- Пороги выбраны только на FY2017: 43 456 кредитов, 3 952 списания. Эти же данные
  ранее обучали калибратор, поэтому результаты подбора предварительные.
- Перебор включает все уникальные вероятности и границы 0/1. Одинаковые значения
  скоринга не разделяются; при равном целевом F-score предпочтён больший recall.
- Сначала записан `selection.json`, затем прочитаны FY2018–2019 и FY2020–2026.
  На этих когортах оценены фиксированные пороги, повторного подбора не было.
  Эти данные уже участвовали в исторической оценке пакета: это существующий
  ретроспективный benchmark, а не новая внешняя проверка.
- F1 одинаково учитывает precision и recall. В F2 пропущенные списания имеют
  больший вес: `F2 = 5*TP / (5*TP + FP + 4*FN)`.
- Recall >=95% — принятое допущение эксперимента, не согласованный бизнес-лимит.
- Пороги 0.15/0.35 ниже — бинарные ориентиры. Java использует эти границы в
  многосоставной политике с платёжной нагрузкой и альтернативным предложением;
  метрики бинарного флага не равны метрикам итоговых отказов.

По сравнению с бинарным ориентиром 0.35 кандидат 0.054874 выявляет на **809**
списаний больше и сокращает пропуски с 1 266 до 457 (**на 63,90%**). Цена —

найденное списание. По сравнению с 0.15 — 338 дополнительных списаний и 7 015
дополнительных ложных флагов, около 20,8 на одно дополнительное списание.
Флаг здесь означает направление на проверку, а не автоматический отказ.

и 0.4088 соответственно. Это показывает дополнительную зависимость от состава
кредитов и ограничивает выводы по агрегированной метрике.

## Практический вывод

Для дальнейшего offline-исследования при приоритете выявления списаний полезен
кандидат **0.054874**; строгая оптимизация F2 предлагает более умеренный **0.164298**.
Порог максимума F1 **0.387527** на поздних данных пропускает слишком большую долю
списаний для заявленного акцента на recall. При этом 0.054874 существенно увеличивает
нагрузку на проверку и не обеспечивает стабильную полноту по годам.

Следующая работа, **не выполненная в этом эксперименте**: подтвердить доступность
срока кредита на момент заявки, разобрать изменения состава и исходов когорт,
обучить/калибровать новую версию на более актуальных зрелых данных и выделить
новый временной holdout. Затем выбрать бизнес-минимум recall и допустимую нагрузку
на проверку. Проверенные здесь test/transfer не должны становиться источником
подбора порога с последующим заявлением о независимой проверке на тех же данных.

Пакет модели, API, база и действующая Java-политика не менялись. Исторические
SBA-данные завершённых кредитов остаются demo-прокси: доступность изменяемого срока
исторически не подтверждена, пересечение заёмщиков не исключено, пригодность для
российской банковской PD и будущих кредитов не установлена.
