# PostgreSQL: проектирование кредитного кабинета

Версия 1, 20.10.2026. Заемщики: ИП и ООО. Объем текущей реализации — хранение и целостность данных хакатона; банковский учет и реальные платежные интеграции не реализованы.

## 1. Главная модель

Учетная запись отвечает за вход. Компания/ИП отвечает за сведения о бизнесе. Заявка отвечает за конкретный запрос на кредит. Документы и проверки привязаны к конкретному субъекту и конкретной заявке.

```text
Пользователь → доступ к компаниям → компания → много заявок
Предварительная форма → запуск рекомендаций → версии продуктов
Заявка → участники → документы и согласия
Заявка → неизменяемая отправленная версия → проверки и скоринг → решение
Решение → предложение → принятие → договор → первая демо-выдача
```

Один пользователь может представлять несколько компаний; у компании может быть несколько пользователей. Директор, собственник и поручитель могут вообще не иметь учетной записи сайта. Их все равно можно учесть как участников сделки.

Доступ `OWNER` означает администрирование кабинета компании, а не доказательство юридического права подписать договор. Нельзя выдавать доступ к компании только потому, что человек ввел ее публичный ИНН.

## 2. Границы системы

React → HTTPS/Nginx → Spring Boot REST API → PostgreSQL. Отдельный закрытый файловый сервис хранит документы; PostgreSQL хранит ссылки, версии и контрольные суммы. В MVP файловый сервис может быть локальным каталогом за backend; для масштабирования — закрытое S3-совместимое хранилище. Его подключение еще предстоит реализовать.

React и Nginx не получают логин/пароль БД. Nginx не раздает каталог загруженных документов как публичную статику. Доступ к каждому скачиванию проверяет backend; имя файла/UUID не дает право доступа.

Начальная архитектура — модульный монолит, одна БД и схема `credit`. Redis, Kafka и отдельная БД рекомендаций на этом этапе не требуются. Для фоновой обработки предусмотрен outbox.

## 3. Таблицы и ответственность

### Вход и бизнес

| Таблица | Назначение и основные данные |
|---|---|
| `app_user` | UUID, `login`, `password_hash`, отображаемое имя, контакты, статус, даты, `row_version`. Логин уникален без учета регистра |
| `user_role` | Глобальные роли `CLIENT`, `BANK_ANALYST`, `BANK_APPROVER`, `COMPLIANCE`, `ADMIN`; несколько ролей у пользователя |
| `party` | ООО, ИП или физлицо: название/ФИО, ИНН, ОГРН/ОГРНИП, регистрация, адрес. Чувствительные идентификационные данные — зашифрованный блок и идентификатор ключа |
| `party_membership` | Пользователь ↔ компания, роль в кабинете, кто и когда выдал доступ, отзыв доступа |
| `party_relation` | Владение, руководство, представительство, бенефициар, группа; доля, сроки и основания полномочий |
| `business_profile` | Текущие фактические сведения: режим налогов, начало работы, регионы/деятельность, дополнительные данные и источники |

Не объединяем ООО и его директора. ИП и то же физлицо в роли поручителя могут иметь отдельные записи `IP`/`PERSON`, связанные отношением `IP_OWNER`. ИНН уникален внутри вида субъекта. Проверка формата ИНН/ОГРН в SQL не проверяет контрольные цифры и реальное существование — это дополнительные проверки backend и источника.

Пароль хранится только как результат `PasswordEncoder`: `{bcrypt}...` или `{argon2}...`. SQL проверяет маркер формата, а не криптографическую корректность хеша. Хеширование, проверка пароля, ограничение попыток и управление сессиями относятся к будущему модулю Spring Security. Не сериализовать сущность пользователя напрямую в ответ API.

### Подбор и каталог

| Таблица | Назначение и основные данные |
|---|---|
| `preliminary_profile` | Черновик короткой формы: владелец либо хеш анонимного токена, версия формы, ответы, источники, срок хранения |
| `credit_product` | Стабильная карточка: код, банк, название, признак демо и доступность |
| `credit_product_version` | Неизменяемые условия версии: сумма, срок, валюта, ставка, формы заемщика, цели, политика и период действия |
| `recommendation_run` | Снимок входного профиля и версии модели/политики конкретного подбора |
| `recommendation_item` | Ранжированные версии продуктов, оценка, применимость и объяснение |

Пользователь может заполнить предварительную форму без файлов. Анонимный токен генерируется криптографически случайным; в БД хранится его SHA-256. Backend задает срок хранения и удаляет/обезличивает истекшие анонимные черновики по политике; это не архив кредитного досье.

Каталог выбирает последнюю доступную версию продукта на дату запроса. Рекомендация и заявка сохраняют точный `product_version_id`; изменение каталога не меняет старые заявки. Текстовое название продукта не использовать как внешний ключ. Повторный расчет рекомендаций создает новый запуск.

### Заявка и финансы

| Таблица | Назначение и основные данные |
|---|---|
| `loan_application` | Номер, заемщик, автор, назначенный сотрудник, версия продукта, сумма/срок/цель, статус, текущий черновик, активная отправленная версия, `row_version` |
| `application_party` | Участники заявки: заемщик, поручители, залогодатели, представители; роли и дополнительные сведения |
| `application_revision` | Неизменяемая отправленная версия: ответы, снимки участников и финансов, источники, хеш, доказательство подачи и автор |
| `financial_statement` | Набор финансовых наблюдений за период: выручка, поступления, расходы, прибыль, долг, платежи, валюта, источник и степень проверки |

Номер заявки — последовательный публичный номер, UUID — внутренний идентификатор. Пропуски последовательности допустимы. UUID и номер не являются секретами доступа.

Финансы хранятся отдельными наборами наблюдений; уточнение создает новую запись, не перезаписывает старую. Отправленный снимок содержит использованные значения/ID. Более поздние подтверждения фиксируются документами, проверками и `input_manifest` запуска модели. Выручка и поступления на счет — разные поля. Неизвестное значение — `NULL`, а не `0`; убыток допускает отрицательный `net_profit`.

Смена статуса сама по себе не равна отправке: отправка требует новой `application_revision`. После дозапроса измененный комплект подается новой версией. Проверки предыдущей версии не становятся проверками новой автоматически.

### Документы

| Таблица | Назначение и основные данные |
|---|---|
| `document_type` | Справочник из 35 типов документов; это каталог типов, а не список обязательных файлов для всех |
| `document` | Логический документ: заявка, субъект, тип и название |
| `document_version` | Файл конкретной версии: закрытый ключ хранения, оригинальное имя, MIME, размер, SHA-256, период, автор загрузки |
| `document_review` | Отдельные результаты проверки файла: антивирус, формат, подпись, подлинность, содержание |
| `application_document_requirement` | Что требуется, от кого, по какой причине/политике, к какому этапу, статус и применимое исключение |
| `requirement_document` | Какой конкретной версией документа выполняется требование |
| `revision_document` | Зафиксированный файловый комплект отправленной версии |

Составные внешние ключи не позволяют выполнить требование файлом из другой заявки, от другого субъекта или другого типа. Один файл может подтверждать несколько совместимых требований, а одно требование — несколько файлов/периодов.

`document_version` и результаты проверок неизменяемы. Исправленный файл — новая версия. Новый результат проверки — новая запись. Поля файла не заменяют проверку реальных байтов в хранилище; ключи хранения нельзя переиспользовать для других байтов. Удаление/сроки хранения согласуются с политикой досье, а не с каскадным удалением пользователя.

Наличие файла не означает `VERIFIED`. Перевод требования в этот статус выполняет доверенный backend после необходимых успешных проверок, включая антивирус. Клиент не передает `verified=true` как основание. Для `LAW` запрещен статус `WAIVED`; неприменимость правового требования должна иметь проверенное основание. Одинаковое имя файла не означает одинаковое содержание.

При отправке достаточно допустимого приемного статуса документа; к решению/подписанию/выдаче соответствующие требования должны быть проверены. Сроки хранятся в `required_before`: `SUBMISSION`, `DECISION`, `SIGNING`, `DISBURSEMENT`, `SERVICING`, `CLOSURE`.

### Согласия и источники

| Таблица | Назначение и основные данные |
|---|---|
| `consent` | Отдельный субъект, вид согласия, получатель, цель, версия текста, подписанное содержание, хеш, доказательства, дата и срок |
| `consent_revocation` | Неизменяемое доказательство отзыва согласия |
| `external_request` | Субъект, источник, основание доступа, согласие при необходимости, уникальный ключ операции, результат и признак имитации |

Для `BKI_MAIN_REPORT` БД требует соответствующее действующее согласие `CREDIT_REPORT` того же субъекта и заявки, с нужным получателем; истекшее или отозванное согласие не принимается. Это специальное правило основного отчета, а не утверждение, что любые сведения БКИ всегда доступны только таким способом.

Содержание согласия, полномочия подписанта, цель, объем доступа и особенности срока проверяет backend по соответствующей процедуре. Значение `valid_until` не вычисляется универсальным SQL `+ 6 months`: применимость продления и основания должны быть установлены отдельно. Статус согласия не заменяет правовую оценку. Основание обработки ПДн требуется уже при сборе данных, а не только при финальном отправлении.

Блокировка записи согласия сериализует регистрацию запроса и отзыв. Если между созданием задания и фактическим обращением к источнику прошло время, worker повторно проверяет основание непосредственно перед обращением. Отзыв не удаляет историю ранее правомерных операций.

`REQUESTED`, `SUCCEEDED`, `NOT_FOUND`, `ERROR`, `CANCELLED` — разные состояния. Отсутствие записи и недоступность сервиса не превращаются в положительный результат проверки. Полные чувствительные ответы источников хранятся закрыто; в `response_summary` только необходимые сведения. В хакатоне источники явно помечаются `is_simulated`.

### Проверки, модели, решения

| Таблица | Назначение и основные данные |
|---|---|
| `application_check_requirement` | Зафиксированный план проверок версии заявки: код, версия правила, правовой характер и этап |
| `check_run` | Неизменяемый результат правила: `PASS`, `FAIL`, `REVIEW`, `UNKNOWN`, `ERROR`, `NOT_APPLICABLE`; хеш входов и доказательства |
| `assessment_run` | Запуск `SCORING` или `FUZZY`: версия модели и признаков, входной комплект, выход и признак синтетики |
| `credit_decision` | Самостоятельное решение уполномоченного сотрудника: исход, обоснование, сумма, срок, ставка, условия и срок действия |
| `loan_offer` | Версия предложения по решению, условия и хеш; однократный ответ клиента с доказательством |

План проверок создается сервером из версии политики, а не принимается от React. План и первоначальный файловый манифест формируются до запечатывания отправки. Пустой план не позволяет одобрить заявку. Полнота состава юридических проверок остается ответственностью серверного набора правил; SQL не может вывести ее из законодательства самостоятельно.

Результат проверок всегда относится к `revision_id`. Позднейший результат определяется последовательным `run_number`, а не только временем: несколько записей одной транзакции могут иметь одинаковое `now()`. Повторная проверка не стирает первую.

Для положительного решения необходимы текущая версия, статус рассмотрения, подтвержденные документы и все соответствующие результаты проверок. Правовой отказ не должен ждать полного финансового пакета, поэтому отрицательный исход может фиксироваться раньше. `decided_by` должен иметь действующую роль `BANK_APPROVER`. Наличие роли не заменяет внутренние лимиты полномочий — их предстоит реализовать в сервисе.

Скоринг/нечеткая логика не изменяют правовой запрет. Модель выдает предложение, сотрудник фиксирует решение. Формула нечеткой логики и оценка качества модели — отдельные будущие задачи. Выход демо-модели нельзя выдавать за проверенную вероятность дефолта.

### Договор, выдача, история и задачи

| Таблица | Назначение и основные данные |
|---|---|
| `loan_contract` | Подписанный кредитный договор, принятое предложение, файл и доказательства подписи; признак имитации |
| `disbursement` | Одна первая демонстрационная выдача по заявке: договор, сумма, валюта, уникальный ключ операции и доказательство |
| `application_status_history` | Автоматическая история переходов, автор и причина; прямое изменение запрещено |
| `audit_event` | Добавляемые события действий, субъект действия и безопасные метаданные |
| `outbox_event` | Фоновые задания в той же транзакции, попытки, доступность, завершение и код ошибки |

На текущем этапе договор/выдача — минимальная демонстрационная модель. Она не рассчитывает проценты, не ведет бухгалтерские проводки, не поддерживает повторные выборки возобновляемой линии и не доказывает отсутствие долга сама. Закрытие опирается на результаты соответствующих проверок; в хакатоне они синтетические. `UNIQUE(application_id)` намеренно ограничивает первую выдачу и основной договор одной записью.

Идемпотентность outbox — обработка «как минимум один раз» с повторяемыми операциями. `UNIQUE(operation_key)` предотвращает повторную запись демо-выдачи; для реального перевода дополнительно нужны идемпотентный платежный API и сверка внешнего результата. Одна SQL-уникальность не предотвращает повторный внешний перевод.

В аудите не хранить пароли, токены, паспортные страницы, полный ответ БКИ и содержимое файлов. История статусов пишется триггером с фиксированным `search_path`; runtime-роли не разрешена прямая вставка в эту таблицу. Общий аудит действий, кроме истории статусов, должен записывать будущий сервис — он не возникает автоматически для каждого UPDATE.

## 4. Типы и индексы

| PostgreSQL | Java 21 / Hibernate | Назначение |
|---|---|---|
| `uuid` | `UUID` | Основные идентификаторы |
| `numeric(19,2)` | `BigDecimal` | Денежные значения без `float`/`double` |
| `numeric(9,5)` | `BigDecimal` | Годовая ставка в процентах: `25` означает 25%, не 0,25 |
| `timestamptz` | `Instant` | Моменты событий; хранение/сравнение в UTC, отображение в часовом поясе пользователя |
| `date` | `LocalDate` | Налоговые и финансовые периоды, даты регистрации |
| `varchar` + `CHECK` | `@Enumerated(EnumType.STRING)` | Контролируемые состояния без привязки к PostgreSQL ENUM |
| `jsonb` | `@JdbcTypeCode(SqlTypes.JSON)` и типизированный объект/`JsonNode` | Изменяемые формы, условия, объяснения и снимки |
| `bigint row_version` | `@Version Long` | Оптимистическая блокировка изменяемых сущностей |

Основные параметры займа, связи, деньги, сроки и статусы типизированы. JSONB используется для действительно переменных частей; это не одна универсальная JSON-таблица на весь проект. Версия формы определяет проверяемую структуру JSON в backend. Текущий SQL контролирует базовую форму объекта/массива, а не все поля анкеты.

Индексы предусмотрены на логин, ИНН/регистрацию, доступ пользователя, очереди заявок, документы, проверки, историю, незавершенные внешние запросы и outbox. GIN на каждый JSONB не создается заранее: добавляется миграцией под измеренный запрос. ИНН хранится строкой; начальные нули не теряются.

Hibernate не должен создавать/обновлять схему: только Flyway и `ddl-auto: validate`. Отношения загружаются лениво, наружу отдаются DTO. Не применять `CascadeType.REMOVE` к досье. `row_version` повышает JPA при `@Version`; триггер обновляет только `updated_at`. Для прямого SQL нужен `UPDATE ... WHERE id = :id AND row_version = :expected` и явное увеличение версии с проверкой числа измененных строк.

## 5. Транзакции

**Отправка заявки:** проверить аутентификацию/доступ/полномочия → заблокировать заявку → проверить версию черновика → сформировать серверный комплект требований → создать `application_revision` → зафиксировать `revision_document` и план проверок → установить активную версию и `SUBMITTED` → записать аудит и outbox → commit. Ошибка откатывает все. Нельзя сначала отправить внешнее задание, а потом пытаться сохранить заявку.

**Рассмотрение:** результат источника и проверки добавляются к заданной версии; перед действием сверяется, что версия остается актуальной. Создание решения и переход в соответствующий статус происходят в одной транзакции с блокировкой заявки. Проверка полномочий сотрудника, лимитов и разделения обязанностей выполняется сервером.

**Принятие предложения:** проверить доступ и право подтвердить действие → заблокировать заявку/предложение → записать доказательство принятия точной версии → сменить статус → аудит. Новый текст условий — новая версия предложения.

**Выдача:** заблокировать заявку → повторно проверить условия → проверить/использовать ключ операции → зафиксировать демонстрационную операцию → изменить статус → аудит/outbox. Для реального внешнего платежа нужен отдельный согласованный протокол, а не вызов платежного сервиса внутри длительной SQL-транзакции.

Фоновые workers выбирают outbox с `FOR UPDATE SKIP LOCKED`, используют идентификаторы заявки/версии в задании и не применяют устаревший результат к новой версии. Продолжительные внешние вызовы не должны удерживать пользовательскую транзакцию. Реализация диспетчера, повторов и восстановления после сбоя — следующий шаг backend.

## 6. Разделение доступа

`credit_migrator` владеет схемой и применяет миграции. `credit_app` не владеет таблицами, не создает объекты, не меняет каталог и историю Flyway; изменяемые и добавляемые данные имеют разные права. PostgreSQL administrator используется только инициализатором локального контейнера.

Проверка доступа к строкам пока проектируется на уровне Spring Security + сервисов и запросов по `party_membership`. **RLS не включен**: сама схема не обеспечивает изоляцию компаний при произвольном SELECT от runtime-роли. Не публиковать универсальные CRUD endpoints или прямой SQL от клиента. Банк получает доступ по рабочей роли, назначению/очереди и политике; массовое чтение всех досье не должно быть следствием одной роли `CLIENT`.

Если позже добавить RLS, необходимы отдельная модель банковского доступа, транзакционный контекст и проверка очистки контекста пула соединений. Владельцы таблиц и superuser могут обходить RLS; включение без такого проектирования не решает авторизацию.

Ключи шифрования, пароли БД и токены интеграций не хранятся в таблицах или Git. Для ключей — отдельный секрет/хранилище, в строке только `encryption_key_id`. Сроки хранения и удаление категорий досье реализуются отдельной политикой; append-only защищает от повседневных изменений, но не является WORM-защитой от администратора и резервного копирования не заменяет.

## 7. Что развивать следующим

1. JPA-сущности, Spring Security, безопасная выдача доступа к компании, банковские полномочия и DTO.
2. Серверные валидаторы версий форм, компилятор документов/проверок из политики продукта, юридические основания и применимость.
3. REST API, транзакционный submit, outbox worker, локальные адаптеры источников и файловый сервис.
4. Полноценные обеспечение и подписи: отдельные объекты залога, поручительства, регистрационные события, версии договоров и дополнительные соглашения.
5. Для реального обслуживания: счета/договорные обязательства, транши и лимиты, начисления, версии графиков, платежи и распределение, ковенанты, просрочка, закрытие и освобождение обеспечения.

Эти расширения требуют новых миграций; действующие `V1–V4` после применения не редактируются.
