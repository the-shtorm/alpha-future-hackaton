# Как сведения форм попадают в БД

## Предварительная форма

`preliminary_profile.answers` содержит данные для подбора; `form_version` фиксирует схему формы. Текущая версия структуры берется из `docs/reference/preliminary-form.md`, а не автоматически из старого макета полной формы.

| Группа | Где хранить | Источник |
|---|---|---|
| Цель, сумма, срок, способ использования, нужная дата | `preliminary_profile.answers.request` | Заявитель |
| ИНН, название, вид заемщика, регистрация, зарегистрированные виды деятельности и адрес ООО | `answers.registration`; при подтверждении — соответствующие поля `party` | Публичный источник или явный ручной ввод при недоступности, с разным статусом проверки |
| Фактические деятельность, регион, начало работы, режим налогов | `answers.business`; текущий профиль после проверки прав — `business_profile` | Заявитель; доступные подтверждения позже |
| Выручка и период, сезонность, остаток долга, платежи, просрочки | `answers.financial` | Заявитель; разрешенные данные своего банка лишь частично дополняют общую картину |
| Готовность к залогу/поручителю, собственные средства | `answers.security`, `answers.project` | Заявитель |
| Дополнительные поля по цели: контракт, покупка, маркетплейс, счет | Условные разделы `answers` | Заявитель или подключенный источник с подходящим основанием |
| Возраст бизнеса, предварительная нагрузка и применимость продуктов | Снимок `recommendation_run`, результат `recommendation_item` | Расчет системы с версией правил |

В профиле не хранить пароль, паспортный скан, сырой отчет БКИ или признак «одобрено». Результат подбора не является решением банка.

Пример происхождения поля в `field_sources`:

```json
{
  "financial.revenue": {
    "kind": "APPLICANT",
    "source_code": "MANUAL",
    "observed_at": "2026-10-20T09:00:00Z",
    "period_from": "2025-10-01",
    "period_to": "2026-09-30",
    "verification_status": "DECLARED"
  },
  "registration.name": {
    "kind": "EXTERNAL",
    "source_code": "FNS_REGISTRY_MOCK",
    "observed_at": "2026-10-20T09:00:00Z",
    "verification_status": "SIMULATED"
  }
}
```

Факт недоступности источника фиксируется отдельно; ручное значение не превращается в ответ ФНС. Исходные регистрационные данные не затираются «исправлением» фактического адреса. Для интеграций хранится явный признак имитации.

## Полная заявка

| Данные | Место хранения |
|---|---|
| Заемщик и контакты кабинета | `party`, `app_user`, `party_membership` |
| Директор, владельцы, бенефициары, представители | `party`, `party_relation`; конкретные участники — `application_party` |
| Выбранный продукт и версия условий | `loan_application.product_version_id` |
| Запрашиваемые сумма, срок, валюта, цель | Типизированные поля `loan_application` |
| Дополнительные ответы, адреса деятельности, группа, долговой реестр, проект и предполагаемое обеспечение | `loan_application.draft_answers` с проверкой версии схемы |
| Финансовые показатели и период | `financial_statement`; использованные значения/ID фиксируются в снимке |
| Файлы и результаты их проверок | `document`, `document_version`, `document_review` |
| Применимые требования к файлам | `application_document_requirement`, `requirement_document` |
| Поданная анкета и ее комплект | `application_revision`, `revision_document` |
| Согласия отдельных субъектов | `consent`, `consent_revocation` |
| Внешние обращения и результаты | `external_request` |
| Проверки и модельные оценки | `application_check_requirement`, `check_run`, `assessment_run` |
| Решение и принятые условия | `credit_decision`, `loan_offer` |

Чувствительные поля удостоверения личности не складываются в общий JSON анкеты: используются защищенный документ/зашифрованный блок `party.sensitive_data_ciphertext`. Примерные формы из `reference` описывают состав вопросов, а не формат безопасного хранения всех ответов в открытом виде.

Пример структуры отправленного `application_revision.snapshot`:

```json
{
  "schema_version": "application-snapshot-v1",
  "request": {
    "product_version_id": "UUID",
    "amount": "1000000.00",
    "currency": "RUB",
    "term_months": 12,
    "purpose": "WORKING_CAPITAL"
  },
  "answers": {},
  "field_sources": {},
  "parties": [],
  "financial_statements": [],
  "document_manifest": [],
  "consent_ids": [],
  "policy_version": "demo-policy-v1"
}
```

Это контракт для будущего серверного валидатора, а не уже исполняемая JSON Schema. БД пока контролирует объект, связи и неизменяемость; backend должен проверить все разделы и соответствие типизированных полей. Денежные значения в API удобно передавать десятичной строкой и преобразовывать в `BigDecimal`; не считать деньги через JavaScript `Number` и Java `double`.

Для хеша фиксируется единый способ сериализации: например, RFC 8785 либо собственная документированная каноническая форма. Нельзя считать хеш от случайного порядка ключей `Map` или текста JSON после произвольного форматирования. Способ канонизации и проверка цифровой подписи — следующий этап реализации; наличие SHA-256 само по себе подписью не является.

## Будущие границы API

| Действие | Какие данные принимает backend | Что клиент не может задавать |
|---|---|---|
| Создать/изменить черновик | Разрешенные поля формы и ожидаемую версию | Чужого владельца, банковские роли, правовой результат |
| Загрузить документ | Содержимое и разрешенные метаданные | `storage_key`, доверенный SHA-256, `VERIFIED`, успешный антивирус |
| Отправить | ID черновика, ожидаемую версию, доказательства действия по процедуре | Произвольный снимок, результаты проверок, статус одобрения |
| Принять предложение | ID точной версии предложения и доказательства | Новую ставку, сумму или срок внутри старой версии |
| Рассмотреть | Данные решения от проверенного сотрудника | `decided_by` другого пользователя, обход лимитов/проверок |

Backend извлекает текущего пользователя из проверенной сессии/токена и самостоятельно устанавливает владельцев, авторов, время и серверные состояния. Значения `created_by`/`decided_by` из тела HTTP-запроса нельзя считать подтвержденными.
