# План обучения, проверки и интеграции кредитного скоринга

Дата: 25 октября 2026 года.
Статус: согласованный план реализации, не отчёт о выполненном обучении.
Основание: исследование ветки `fast_api` и решения, согласованные с пользователем в диалоге.

## 1. Цель, исходное состояние и принятые решения

### Что должно получиться

Обученная модель бинарной классификации, которая оценивает вероятность списания кредита по девяти признакам SBA. FastAPI возвращает прогноз, а Spring Boot использует его вместе с финансовыми проверками для принятия демонстрационного решения:

- `APPROVED`;
- `COUNTEROFFERED`;
- `DECLINED`;
- `REQUEST_INFO`.

**Определение целевого класса остаётся неизменным: `LoanStatus`: 0 = погашен (`false`), 1 = списан (`true`).**

Модель не должна самостоятельно принимать банковское решение или подменять финансовые проверки.

### Что установлено по ветке fast_api

Изучена локальная ветка `fast_api`, коммит `74c4d2ccaad06553c2a9b8fd456c8fd8a7d29a10`. Она совпадала с локальным указателем `origin/fast_api`; рабочее дерево при исследовании и перед экспортом было чистым. Удалённый сервер Git в рамках экспорта не опрашивался.

Текущее состояние:

- FastAPI реализует семантическое ранжирование продуктов через E5.
- Кредитной модели, отдельного API скоринга и Java-клиента для него пока нет.
- [DataPolicy.java](../backend/src/main/java/ru/alphafuture/credit/DataPolicy.java) использует временную `DemoAssessment`; без неё возвращается `ASSESSMENT_UNAVAILABLE`.
- [Payments.java](../backend/src/main/java/ru/alphafuture/credit/Payments.java) уже рассчитывает точный аннуитет с комиссиями.
- [Data Policy 3.0](reference/data-policy-3.0.md) описывает будущую интеграцию, но её ML-часть ещё не реализована.
- БД уже содержит `assessment_run` и ссылку `credit_decision.assessment_id`. Основной аудит оценки можно реализовать без новой таблицы.

Исторический отчёт readiness нельзя использовать как единственное описание текущего FastAPI: ранжирование после него существенно развилось, но кредитный скоринг по-прежнему отсутствует.

### Зафиксированные решения

1. Реализовать полную цепочку: подготовка данных → обучение → настройка → калибровка → FastAPI → Spring Boot → решение → аудит.
2. Сохранить точный аннуитет и комиссии `Payments`.
3. Внедрить правила риска Data Policy 3.0, адаптировав расчёт платёжной нагрузки и контрпредложения к `Payments`.
4. Для российских демо-продуктов разрешить прогноз вне обучающего диапазона с явными предупреждениями.
5. Использовать зрелые когорты для основного эксперимента; новые когорты — отдельно для проверки переноса.
6. Сохранить текущий исходный CSV неизменным. Обучающие представления и разбиения создавать отдельно.
7. Не менять публичные поля preliminary/application, существующий обмен Recsys и исторические решения.
8. Считать результат демонстрационной оценкой списания SBA, а не проверенной российской банковской PD.

### Учёт задачи

Первым шагом реализации создать новый отдельный отчёт в `docs/agents/` с датой и названием задачи, добавить ссылку в общий индекс `docs/agents/log.md`. Отчёт вести по мере выполнения: фиксировать изменения, команды, фактические проверки, версии данных и моделей, ограничения и Git status.

Экспорт настоящего плана имеет собственный [отчёт задачи](agents/2026-10-25-credit-scoring-plan-export.md). Он не заменяет будущий отчёт реализации. При подготовке плана и его экспорте обучение и тестовые комплекты приложения не запускались; проверки документа перечислены в отчёте экспорта.

## 2. Подготовка данных, обучение и настройка модели

### 2.1. Зафиксировать исходный датасет

Использовать подготовленный в этом диалоге `sba_dataset(2010-2026).csv`.

Проверенные параметры:

- 461 559 строк;
- 23 колонки;
- 424 601 погашенный кредит;
- 36 958 списанных кредитов;
- доля положительного класса — 8,0072%;
- пропусков в девяти входных признаках нет.

SHA-256:

```text
eb9efbe801725f70969a1e1128c4ce3b1930c4f34e8820d3d0b81c84f4951e43
```

Проверенная копия из Downloads совпадает с созданным ранее файлом по хешу. Для переносимого запуска путь должен передаваться параметром конфигурации или CLI, а не зашиваться в реализацию.

Подготовка должна прекращаться при неожиданной схеме, изменённом хеше зафиксированной версии, неизвестных кодах или нарушении целостности. Для новой версии данных нужен новый manifest, а не молчаливое продолжение старого эксперимента.

Полный CSV оставить локальным входным артефактом. В Git хранить описание, контрольную сумму и конфигурацию подготовки.

### 2.2. Разделить данные по назначению

**Входы модели X:**

```text
GrossApproval
InitialInterestRate
FixedorVariableInterestInd
TermInMonths
NaicsCode
BusinessType
BusinessAge
RevolverStatus
CollateralInd
```

**Таргет y:**

```text
LoanStatus
```

**Служебные данные:** все компоненты четырёх дат и `ApprovalFY`.

Не формировать X командой «все колонки, кроме LoanStatus»: в этом случае модель получит даты исходов.

Из компонентов дат восстанавливать календарные даты только для проверок и разбиений. Проверять:

- согласованность `ApprovalFY`;
- отсутствие частично заполненных троек даты;
- наличие соответствующей даты исхода;
- `ApprovalDate ≤ eventDate ≤ AsOfDate`.

Структурные пропуски противоположной даты сохранять. Их заполненность не использовать как признак.

### 2.3. Создать единый преобразователь признаков

Обучение и inference должны использовать одну реализацию преобразований, а не два независимо написанных набора правил.

| Поле контракта FastAPI | Поле модели | Преобразование |
|---|---|---|
| `loanAmountUsd` | `GrossApproval` | Decimal string → числовое значение в USD |
| `termMonths` | `TermInMonths` | Положительное целое количество месяцев |
| `initialInterestRatePct` | `InitialInterestRate` | Процентные пункты без деления на 100 |
| `interestRateType` | `FixedorVariableInterestInd` | `FIXED → F`, `VARIABLE → V` |
| `isRevolving` | `RevolverStatus` | `true → Y`, `false → N` |
| `hasCollateral` | `CollateralInd` | `true → Y`, `false → N` |
| `businessType` | `BusinessType` | `CORPORATION → 1`, `INDIVIDUAL → 2`, `PARTNERSHIP → 3` |
| `businessAgeCategory` | `BusinessAge` | Строковая категория → согласованный код 1–9 |
| `naicsCode` | `NaicsCode` | Шестизначная строка; дальнейшее преобразование определяется manifest модели |

`BusinessType`, `BusinessAge` и NAICS остаются категориями. Номер кода не означает количественную величину.

Для `BusinessAge` использовать уже утверждённый справочник:

| Код | Значение |
|---:|---|
| 1 | Стартап, кредит на открытие |
| 2 | Менее 1 года |
| 3 | Новый бизнес / до 2 лет |
| 4 | От 2 до менее 3 лет |
| 5 | От 3 до менее 4 лет |
| 6 | От 4 до менее 5 лет |
| 7 | 5 лет и более |
| 8 | Существующий бизнес / более 2 лет — широкая историческая категория |
| 9 | Смена собственника |

В первой версии сохранять текущую обучающую популяцию без новых фильтров по стартапам, партнёрствам или широким возрастным категориям. Дополнительно показывать качество на срезе категорий, достижимых из действующего backend.

### 2.4. Зафиксировать временные разбиения

| Часть | Финансовые годы | Строк | Списаний | Назначение |
|---|---|---:|---:|---|
| Train | 2010–2014 | 189 354 | 13 308 | Обучение кандидатов |
| Validation | 2015–2016 | 96 113 | 7 151 | Подбор параметров и выбор модели |
| Calibration | 2017 | 43 456 | 3 952 | Настройка вероятностей |
| Test | 2018–2019 | 60 186 | 5 927 | Независимая итоговая оценка |
| Transfer diagnostics | 2020–2026 | 72 450 | 6 620 | Отдельная проверка переноса |

Индексы строк и принадлежность разбиениям сохранять в manifest подготовки. Случайное перемешивание не должно менять принадлежность временным частям.

Это **ретроспективная оценка завершённых кредитов**, а не доказательство исторически реализуемого запуска: часть меток старых кредитов стала известна позднее. Ограничение фиксировать в отчёте.

В текущем CSV нет ID заёмщика. Поэтому отсутствие пересечений компаний между частями гарантировать нельзя. Повторы не удалять автоматически по совпадению признаков; отдельно учитывать их количество и ограничение идентификации.

### 2.5. Обучить базовые варианты

**Константный baseline**

Вероятность равна доле списаний в обучающей части. Он нужен для сравнения Log Loss и Brier Score.

**LogisticRegression**

- Числовые поля: `log1p(GrossApproval)`, ставка, срок.
- Масштабирование числовых полей через `StandardScaler`.
- Категориальные поля — через `OneHotEncoder(handle_unknown="ignore")`.
- Регуляризация L2.
- `C`: `0.01`, `0.1`, `1`, `10`.
- `solver="lbfgs"`, `max_iter=2000`.
- Проверять сходимость; предупреждение о несходимости не считать успешным обучением.

**CatBoostClassifier**

- Числовые поля: исходная сумма, ставка, срок.
- Остальные шесть полей явно передавать как категориальные.
- `loss_function="Logloss"`.
- `iterations=1500`.
- `depth`: `4`, `6`, `8`.
- `learning_rate`: `0.03`, `0.06`.
- `l2_leaf_reg`: `3`, `10`.
- Early stopping: 100 итераций без улучшения на validation.
- `random_seed=42`.
- CPU, четыре потока, последовательный запуск экспериментов.

Для обеих моделей проверить два представления NAICS: полный шестизначный код и двухзначный префикс. Выбранное преобразование зафиксировать в артефакте.

Получится восемь конфигураций логистической регрессии и 24 конфигурации CatBoost. В первом проходе не применять SMOTE, искусственное выравнивание классов или `class_weight="balanced"`.

Категориальная обработка CatBoost должна использовать его штатный механизм, без предварительного ручного one-hot. [Документация CatBoost](https://catboost.ai/docs/en/features/categorical-features).

### 2.6. Выбрать модель и откалибровать вероятность

Основной критерий выбора на validation — минимальный Log Loss. Дополнительно учитывать PR-AUC, ROC-AUC и размер артефакта.

Если Log Loss логистической регрессии находится в пределах 0,5% от лучшего результата, выбирать её как более простой вариант.

После выбора:

1. Зафиксировать семейство, параметры и представление NAICS.
2. Переобучить выбранный вариант на FY2010–2016.
3. Для CatBoost использовать зафиксированное число итераций, найденное при настройке; не использовать calibration для early stopping.
4. На FY2017 обучить sigmoid-калибратор на необработанном выходе выбранной модели.
5. Зафиксировать весь пакет до открытия итогового теста.

Калибратор не обучать на train, validation или test. Проверять, что положительному классу соответствует именно списание. [Документация по калибровке](https://scikit-learn.org/stable/modules/calibration.html).

Отдельно провести диагностическое сравнение со схемой без `TermInMonths` на development-данных. Это не меняет утверждённый девятиполевой HTTP-контракт. Результат нужен для оценки чувствительности к неподтверждённому историческому смыслу срока. Подтверждённая утечка через срок блокирует выпуск до исправления подготовки.

### 2.7. Итоговый отчёт качества

На независимом тесте рассчитать:

- ROC-AUC;
- PR-AUC в определении Average Precision;
- Log Loss;
- Brier Score;
- калибровочную диаграмму с количеством наблюдений в каждом интервале;
- precision, recall, долю списаний и объём заявок при порогах 0,15 и 0,35;
- качество по годам, отрасли, типу бизнеса, возрасту, линии и обеспечению.

FY2020–2026 оценивать отдельно после фиксации модели. Не использовать эти результаты для изменения параметров с сохранением прежнего статуса «независимой проверки».

Минимальные условия выпуска:

- ROC-AUC выше 0,5;
- Average Precision выше доли положительного класса в тесте;
- Log Loss и Brier лучше константного baseline;
- нет обнаруженных прямых утечек;
- опубликованы ограничения калибровки и недостаточно представленных групп.

Это минимальные технические условия, а не доказательство банковской пригодности. При провале условий модель не активировать и не заменять вымышленными метриками.

## 3. API скоринга, модельный пакет и FastAPI

### 3.1. Добавить отдельный контракт

Новый внутренний endpoint:

```text
POST /api/v1/scoring/evaluate
Authorization: Bearer <internal key>
```

Не использовать для этого endpoint ранжирования и не менять его payload.

Запрос содержит:

- `schemaVersion`: фиксированное значение `sba-scoring-1`;
- `requestId`: UUID;
- девять полей из таблицы преобразований.

Правила типов:

- `loanAmountUsd` — положительная decimal string с двумя знаками;
- `termMonths` — строгий integer `1..360`, без принятия Boolean или `12.0`;
- `initialInterestRatePct` — неотрицательная decimal string, до пяти дробных знаков, без деления на 100;
- `interestRateType` — `FIXED` или `VARIABLE`;
- два флага — строгие JSON Boolean;
- `businessType` — строковый enum SBA;
- `businessAgeCategory` — строковый enum девяти согласованных категорий;
- `naicsCode` — строка из шести цифр;
- неизвестные поля запрещены.

Нулевая ставка технически допустима для backend-платежей, но должна сопровождаться предупреждением о выходе за обучающую область, если модель обучалась только на положительных ставках.

### 3.2. Зафиксировать ответ

Все поля ответа обязательны:

| Поле | Смысл |
|---|---|
| `schemaVersion` | `sba-scoring-1` |
| `requestId` | Идентификатор исходного запроса |
| `sbaDefaultProbability` | Конечное число `[0,1]`, вероятность класса 1 |
| `score` | Целое `0..100`, `100 × (1 − p)` |
| `modelVersion` | Идентификатор конкретного пакета модели |
| `featureVersion` | Версия правил преобразования |
| `calibrationVersion` | Версия калибратора |
| `domainStatus` | `IN_RANGE` или `EXTRAPOLATION` |
| `isDemo` | `true` для данного выпуска |
| `warnings` | Список кодов предупреждений |

`score` округлять с `ROUND_HALF_UP`, одинаково в Python и Java. Вероятность для политики не округлять до целых процентов и не восстанавливать из балла.

FastAPI не возвращает `APPROVED` или `DECLINED`: эти решения принадлежат Spring Boot.

### 3.3. Обработка ошибок

Использовать действующий формат `error/code/message/details/requestId`.

- `401` — отсутствующий или неправильный внутренний ключ;
- `422` — неверный контракт;
- `503 MODEL_NOT_READY` — модель недоступна;
- `503 SERVICE_BUSY` — исчерпана очередь;
- `500` — непредвиденная ошибка без выдачи внутренних подробностей.

Обновить обработчик validation errors: сейчас он различает контракты ранжирования и не знает о scoring. Добавить безопасное описание полей нового запроса.

Выход за обучающий диапазон — не ошибка JSON-контракта. По выбранному режиму возвращать прогноз с предупреждениями, без искусственного ограничения ставки или суммы обучающим максимумом.

### 3.4. Контроль области применимости

Сохранять в пакете диапазоны и частоты категорий фактического обучающего набора.

Предупреждения должны покрывать:

- сумму, ставку или срок за обучающим диапазоном;
- неизвестный обучению NAICS/префикс;
- редкую категорию с менее чем 50 обучающими наблюдениями;
- перенос SBA США на российский демонстрационный продукт;
- неподтверждённую историческую доступность изменяемого срока.

В текущем демо-каталоге ставки 21–30%, тогда как максимум полного CSV — 16,5%. После обучения границы брать из конкретного обучающего набора, а не жёстко зашивать 16,5%.

Предупреждения сохраняются в решении. Они не отменяют прогноз в согласованном демо-режиме и не превращают его в проверенную российскую PD.

### 3.5. Пакет модели

Создать версионируемый пакет, содержащий:

- выбранный классификатор;
- препроцессор и словари категорий;
- калибратор;
- порядок девяти признаков;
- определение положительного класса;
- версии и хеши данных;
- параметры обучения и разбиения;
- диапазоны применимости;
- итоговые метрики;
- контрольные суммы всех загружаемых файлов.

Для CatBoost сохранять нативный `.cbm`; для логистической регрессии — обученный sklearn pipeline. Сериализованные Python-объекты загружать только из доверенного пакета после проверки manifest и контрольных сумм.

Хранить единственную выбранную модель для inference. Не загружать одновременно все экспериментальные варианты.

Зависимости закрепить lock-файлом с Python 3.11. Обучение табличного скоринга отделить от существующего CUDA-окружения обучения E5. Не менять E5 checkpoint, его пороги или идентичность.

### 3.6. Runtime

- Загружать скоринговый пакет один раз при старте.
- Создать отдельные scoring runner и флаг готовности.
- Использовать один inference-поток и очередь максимум из четырёх запросов.
- Ограничить ожидание места в очереди одной секундой.
- Не выполнять синхронный inference в event loop.
- Не освобождать занятый слот раньше завершения фактического вычисления при отмене HTTP-запроса.
- Добавить внутренние scoring model-info и scoring readiness.
- Сохранить смысл существующего readiness ранжирования: отключённый scoring не должен ломать Recsys.

При неправильном пакете scoring остаётся неготовым и возвращает 503. Автоматической подмены на фиксированные веса нет.

## 4. Подключение Spring Boot и правила решения

### 4.1. Подготовка признаков на стороне Java

Spring формирует запрос из подтверждённой ревизии заявки и выбранной версии продукта.

Правила:

- сумма USD: `request.amount / 90.00`, округление до двух знаков `HALF_UP`;
- ставка: исходные процентные пункты продукта, без деления на 100;
- срок: `request.termMonths`;
- тип ставки и механизм финансирования: из серверного каталога;
- обеспечение: `collateralReady == YES` и положительная стоимость;
- `LLC → CORPORATION`, `IP → INDIVIDUAL`;
- возраст — полные месяцы до зафиксированного `asOf`, затем согласованная категория.

Для поданной ревизии сохранять действующее поведение: `asOf` берётся из времени подачи. Для предварительного validate используется текущий UTC-момент.

Маппинг отраслей зафиксировать в коде и документации:

| Отрасль приложения | NAICS |
|---|---|
| `TRADE` | `445110` |
| `MANUFACTURING` | `332710` |
| `SERVICES` | `811111` |
| `IT` | `541511` |
| `CONSTRUCTION` | `236220` |
| `AGRICULTURE` | `111998` |
| `LOGISTICS` | `484110` |

Это демонстрационное приближённое сопоставление общих отраслей, а не точное восстановление классификации каждой компании.

До вызова модели сохранять проверки обязательных полей. Неизвестное значение не превращать в ноль, false или категорию по умолчанию.

### 4.2. Java gateway

Добавить отдельный typed gateway скоринга:

- серверный URL и ключ из конфигурации;
- Bearer-аутентификация;
- connect timeout 500 мс;
- общий deadline одного вызова 2 секунды;
- без перенаправлений и автоматических повторов;
- ограничение ответа 64 КиБ;
- строгая проверка JSON, версии схемы, requestId, вероятности, балла и metadata.

Несовпадение балла с вероятностью, NaN/Infinity, выход вероятности за `[0,1]`, неизвестная версия или неправильный requestId считаются невалидным ответом.

При недоступности сервиса возвращать `REQUEST_INFO` с технической причиной. Не считать отказ связи низким риском и не переключаться на `DemoAssessment`.

### 4.3. Новая версия политики

Ввести отдельную версию, например:

```text
data-policy-3.0-sba-annuity-1
```

Она явно отличается от исходной 3.0 тем, что сохраняет точный аннуитет `Payments`.

Порядок обработки:

1. Проверить формат и полноту заявки, применимость продукта и существующие обязательные ограничения.
2. При `financial.overdue > 0.20` — `DECLINED`, без контрпредложения и без вызова модели.
3. Проверить полные месяцы выручки, положительную среднемесячную выручку, обеспечение, собственный взнос, LTV и наличие поддерживаемого графика.
4. Получить действующий серверный макроконтекст один раз и сохранить его идентичность.
5. Рассчитать платёж исходных условий через `Payments`.
6. Вызвать scoring для исходных девяти признаков.
7. Рассчитать:

```text
p_final = min(1, p_sba + 0.50 × overdue)
PTI = (existingMonthlyDebtPayment + newMonthlyPayment)
      / averageMonthlyRevenue
```

8. Если `p_final ≤ 0.15`, `PTI ≤ 0.40` и выполнены остальные ограничения — `APPROVED`.
9. Если `p_final > 0.35` — `DECLINED`.
10. Иначе попытаться сформировать разрешённое продуктом контрпредложение.
11. При отсутствии подходящего варианта — `DECLINED`; при недостатке данных или конфигурации — `REQUEST_INFO`.

В `conditions` всегда сохранять `missingFields` как список, включая пустой список: это требуется существующей логикой `ApplicationService`.

`p_final` — **индекс риска после применения политики**, а не автоматически откалиброванная вероятность. Калибровка относится к `p_sba`.

### 4.4. Контрпредложение

Рассчитать ставку:

```text
altRatePct = max(
    baseRatePct,
    keyRatePct + 5 + 20 × initial_p_final
)
```

Проверить ограничения продукта, включая разрешённые изменения и максимальную ставку.

Срок увеличивать максимум на 12 месяцев только при превышенной нагрузке и явном разрешении изменения срока. В действующем каталоге `termChangeAllowed=false`, поэтому по умолчанию срок сохраняется.

Платёжный бюджет:

```text
budget = 0.40 × averageMonthlyRevenue
         − existingMonthlyDebtPayment
```

Максимальную сумму находить по **той же функции Payments**, включая комиссии и округления. Для фиксированного срока/ставки допустим двоичный поиск суммы с точностью до копейки. Поиск не должен многократно вызывать ML.

Учитывать минимум и максимум продукта, исходную сумму, LTV и допустимый срок.

После получения одного допустимого кандидата:

1. Повторно вызвать модель с альтернативной суммой, ставкой и сроком.
2. Пересчитать `p_final`.
3. Повторно проверить PTI.
4. Выдать `COUNTEROFFERED`, только если `p_final ≤ 0.35`, `PTI ≤ 0.40` и все ограничения выполнены.
5. Не создавать контрпредложение, полностью совпадающее с первоначальными условиями.

Максимум — два ML-вызова на один расчёт: исходный и альтернативный. Модельный риск не считать монотонным по сумме/ставке; не искать условия двоичным поиском по прогнозу.

Оба ответа должны относиться к одной версии модельного пакета. При смене версии между вызовами не сохранять положительное решение.

### 4.5. Сохранение оценки и совместимость

В `assessment_run` сохранять отдельные успешные оценки исходных и альтернативных условий:

- ревизию заявки;
- `assessment_kind=SCORING`;
- версии модели и признаков;
- хеш нормализованных входов;
- входной manifest;
- полный ответ и предупреждения;
- демонстрационный статус.

В `credit_decision.assessment_id` записывать оценку выбранных условий. В `conditions` сохранять обе оценки, выбранный вариант, FX, макроконтекст, PTI, `p_sba`, `p_final` и причины решения.

Плоские поля `sbaDefaultProbability` и `finalRiskScore` должны соответствовать выбранным условиям: исходным при одобрении, альтернативным при контрпредложении.

Существующие проверки документов, финансовых операций, ручного рассмотрения, прав сотрудника и принятия точных условий не обходить.

**Отдельно учесть версионирование старых ревизий.** Сейчас требования проверок и `check_run` связаны по `rule_version`. Поэтому нельзя просто заменить глобальную константу версии политики:

- новые ревизии получают новую политику;
- старые сохраняют исходную;
- запись проверок, включая выдачу, использует версию зафиксированной ревизии;
- старые решения и предложения не пересчитываются автоматически;
- для перехода старой заявки на новую политику нужна новая подтверждённая ревизия.

Основной вариант не требует изменения структуры БД: необходимые JSONB-поля и внешние ключи уже есть. Исторические миграции не менять.

## 5. Проверки, выпуск и критерии завершения

### 5.1. Проверки данных и преобразований

Покрыть:

- текущие 23 колонки и контрольную сумму;
- баланс классов и отсутствие пропусков в X;
- восстановление дат и финансового года;
- запрет попадания metadata в X;
- все коды BusinessType/BusinessAge;
- Y/N и F/V;
- NAICS как строку;
- преобразование RUB→USD без повторной конвертации;
- ставку 28% как 28, а не 0,28;
- возрастные границы 12, 24, 36, 48 и 60 полных месяцев;
- одинаковый вектор для эквивалентной строки CSV и HTTP-запроса.

Проверить неизвестные категории и значения вне обучающего диапазона. Числа 0 и false не должны считаться отсутствующими автоматически.

### 5.2. Проверки моделей и пакета

- Сохранение и повторная загрузка не меняют прогноз.
- Положительный класс — именно 1.
- `p` конечна и находится в `[0,1]`.
- Калибратор обучен только на FY2017.
- Test не использовался при выборе конфигурации.
- Повреждённый manifest, неверный хеш или несовместимая версия блокируют готовность scoring.
- В runtime загружается только выбранная модель.
- Повторное обучение сохраняется в новый каталог, не перезаписывая опубликованный пакет.

В CI использовать небольшой реальный тестовый пакет для проверки сериализации, а не только fake scorer. Полный production-пакет проверять отдельным offline smoke.

### 5.3. Проверки HTTP-контракта

- валидный запрос и соответствие JSON Schema;
- отсутствующий/неправильный ключ;
- неправильные типы, лишние поля, неизвестная версия;
- Boolean вместо срока и строка вместо Boolean;
- размер тела и перегрузка очереди;
- неготовая модель;
- корректная обработка отмены запроса;
- отсутствие утечки внутренних исключений;
- совпадение requestId и metadata;
- округление балла, включая `p=0.155 → score=85`;
- OOD-запрос возвращает прогноз с предупреждением.

Дополнить опубликованные OpenAPI и JSON Schema. Существующие схемы ранжирования и их поля сохранить.

### 5.4. Проверки политики и Java-интеграции

Использовать управляемый fake scoring server для точных граничных сценариев:

| Сценарий | Ожидаемое поведение |
|---|---|
| `overdue = 0.20` | Не срабатывает hard reject только по этому условию |
| `overdue > 0.20` | Отказ без ML и контрпредложения |
| `p_final = 0.15`, допустимый PTI | Возможно одобрение |
| `p_final = 0.35` | Возможна проверка контрпредложения |
| `p_final > 0.35` | Отказ |
| `PTI = 0.40` | Граница считается допустимой |
| Нет выручки, периода, макроконтекста или графика | `REQUEST_INFO` по соответствующей причине |
| Альтернативная сумма ниже минимума | Контрпредложение не создаётся |
| Превышен лимит ставки или запрещено изменение | Ограничение продукта не обходится |
| Повторная оценка альтернативы неудовлетворительна | Нет положительного решения |
| Timeout, 401/422/500/503 от ML | Нет автоодобрения и fallback на fixed weights |
| Версия модели изменилась между оценками | Расчёт не завершается положительным решением |
| Старая ревизия политики | Нет ошибки FK и незаметной смены правил |
| Ручное одобрение пытается обойти блокировку | Сохраняется `POLICY_BLOCKED` |

Сохранить регрессионный тест платежа: 1 000 000 RUB, 12 месяцев, 28% → 96 505,99 RUB при соответствующем продукте без дополнительной комиссии.

Проверить сохранение `assessment_run`, ссылок решения, обеих оценок контрпредложения и неизменность исторических записей.

### 5.5. Полная приёмка

В отдельном временном стеке выполнить цепочку:

```text
анкета → eligibility → выбор продукта → заявка →
подача ревизии → документы/проверки →
реальный FastAPI scoring → решение →
принятие условий → подписание → моделируемая выдача
```

Нужны сценарии одобрения, контрпредложения, отказа и запроса информации.

Параллельно проверить действующее ранжирование E5: новая модель не должна менять его ответы, metadata, пороги и обработку кандидатов.

Планируемые проверки проекта:

- Python unit/API tests с сохранением действующего требования покрытия не ниже 95%;
- Ruff;
- Maven tests и `verify`, включая style и JavaDoc;
- PostgreSQL integration tests;
- offline smoke выбранного пакета;
- Java→FastAPI acceptance;
- регрессия существующего Recsys.

Эти команды выполняются при реализации; их успешность в данном плане не заявляется.

### 5.6. Нагрузка и эксплуатация

Проверить одиночный scoring и одновременную работу с E5.

Целевые технические бюджеты первого выпуска:

- p95 scoring endpoint — до 250 мс после загрузки;
- p99 — до 500 мс при четырёх одновременно поступивших запросах;
- один inference-поток scoring;
- сохранение ограничения FastAPI-контейнера 2 GiB;
- проверка общего бюджета сайта 6 ГБ с учётом остальных сервисов и ОС.

Это критерии измерения, а не обещанные результаты. При превышении оптимизировать глубину/размер модели, потоки и очередь; не увеличивать число workers с дублированием E5 и scoring в памяти.

Наблюдать: задержки, ошибки gateway, очередь, версию модели, распределение прогнозов, частоту OOD и решения политики. Не писать полные анкеты и секреты в технические логи.
