# Словарь данных и Политика разметки для ML-скоринга (Data Policy)

Версия 2.1 (С поддержкой встречных предложений и макро-параметров). Документ описывает гибридную архитектуру бэкенда для хакатона. Он объединяет контракты REST API для интерфейсов клиента и сотрудника банка с правилами подготовки признаков (фичей) для линейных моделей машинного обучения на этапе скоринга.

## 1. Общие правила представления и нормализации

Сырые данные анкеты подготавливаются для ML-алгоритма. Все текстовые даты и проценты перед подачей в модель должны быть нормализованы:

| Тип в API / форме | Правило нормализации для ML-вектора | Пример | 
| ----- | ----- | ----- | 
| `money` / `decimal` | Сохраняется как точное десятичное число, без округления до целых | `"1000000.00"` | 
| `percent` | Переводится в долю (fraction) от 0 до 1 путем деления на 100 | `"20.00"` → `0.2000` | 
| `date` / `datetime` | Не подаются в модель напрямую; конвертируются во временные интервалы (стаж в месяцах/днях) | `2020-01-01` → `81` (мес.) | 
| `boolean` | Транслируются в бинарные признаки | `true` → `1`, `false` → `0` | 
| `enum` | Сохраняют исходные коды, в ML используются через One-Hot Encoding | `LLC` / `IP` | 

**Качество данных и обработка пропусков (Missing Values):**
Для корректной работы линейной модели критически важно отличать математический ноль от отсутствия данных. Вводится мета-статус `value_status`:

* `KNOWN`: Значение известно и подтверждено (включая реальные нули, например, "платежей по долгам нет").

* `UNKNOWN`: Данные не заполнены или "клиент не знает" (в вектор модели подается `null` или используется стратегия импутации (заполнения), чтобы не искажать веса).

* `INVALID`: Значение технически невозможно (например, отрицательная выручка).

## 2. Жизненный цикл заявки и роли

В системе предусмотрено два интерфейса: клиентский и банковский (кабинет сотрудника).

**Роли:**

* `OWNER` / `EDITOR` / `VIEWER` — роли на стороне клиента-заемщика.

* `BANK_APPROVER` — глобальная роль сотрудника банка. Позволяет просматривать очередь заявок (`/bank/applications`), брать их в работу (поле `assigned_to`) и инициировать бизнес-решения.

**Маршрут сделки:**

```
DRAFT → SUBMITTED → VALIDATING → ENRICHING → SCORING (ML-модель) → UNDER_REVIEW
      → APPROVED / COUNTEROFFERED → OFFER_ACCEPTED → SIGNED → READY_FOR_DISBURSEMENT → DISBURSED

```

* **Возврат на доработку:** Если на этапе валидации не хватает данных, решение принимает вид `REQUEST_INFO`. Заявка переходит в статус `NEEDS_INFO`.

* **Встречное предложение (Counteroffer):** Если модель отклоняет первоначальный запрос (отказ), но клиент в целом платежеспособен, система формирует решение `COUNTEROFFERED` с измененными условиями.

## 3. Поля окончательной заявки (Входные данные `answers`)

Базовый набор из 15 полей окончательной заявки на кредит. Поля, необходимые только для рекомендательного алгоритма (подбора кредитных предложений), описаны в `preliminary_form.md`; при создании заявки часть из них переносится автоматически и подтверждается клиентом. Все поля ниже относятся к окончательной заявке и используются алгоритмом скоринга для расчета валидности кредитной заявки.

### 3.1. Унаследованные из предварительной формы

Переносятся из `preliminary_form.md` при создании заявки; перечислены только те, что подходят по смыслу окончательной заявки.

* `request.amount` (money): Сумма кредита.

* `request.termMonths` (integer): Срок в месяцах.

* `request.purpose` (enum): Цель (напр., `WORKING_CAPITAL`).

* `registration.borrowerKind` (enum): ИП (`IP`) или ООО (`LLC`).

* `registration.registeredOn` (date): Дата регистрации.

* `business.actualStartedOn` (date): Дата фактического начала деятельности.

* `business.taxRegime` (enum): Налоговый режим.

* `business.mspRegistry` (boolean): Состоит в реестре МСП.

* `financial.revenue` (money): Выручка за выбранный период.

* `financial.periodFrom` / `periodTo` (date): Границы периода выручки.

### 3.2. Поля, заполняемые при подаче заявки (данные для одобрения)

* `financial.monthlyDebtPayment` (money): Текущие платежи по долгам (0 — если нет).

* `financial.overdue` (float): Доля просроченных платежей \[0,1\].

* `security.collateralValue` (money): Предполагаемая стоимость залога.

* `project.ownContributionPct` (percent): Доля собственных средств (0..100).

## 4. Производные признаки и Макро-параметры (Feature Engineering)

На этапе `SCORING` сырые поля преобразуются в расчетные метрики, которые подаются в линейную модель.

### 4.1. Временные интервалы (Time Features)

* `business.registered_age_months`: `full_months(registeredOn, as_of)`. Возраст юридического лица.

* `business.operating_age_months`: `full_months(actualStartedOn, as_of)`. Фактический стаж бизнеса.

### 4.2. Относительные финансовые коэффициенты (Ratios)

* **Доля платежей в выручке (`debt.payment_to_revenue`)**:
  Формула: `monthlyDebtPayment / (revenue / period_months)`.

* **Отношение запрошенной суммы к среднемесячной выручке (`request.amount_to_monthly_revenue`)**:
  Формула: `request.amount / (revenue / period_months)`.

* **Нормализованная доля собственных средств (`project.own_contribution_share`)**:
  Формула: `ownContributionPct / 100`.

### 4.3. Обработка просрочек (Overdue Weighting)

* Если `overdue > 0.2`: Хард-реджект (отказ) без права на встречное предложение.

* Если `0 < overdue <= 0.2`: Линейная модель применяет отрицательный вес, снижая скоринговый балл, что может привести к формированию `COUNTEROFFERED` вместо прямого одобрения.

### 4.4. Встречные предложения и Макроэкономический контекст

В модель скоринга добавляется внешний системный параметр контекста:

* `macroeconomic.key_rate_pct` (decimal): Текущая ключевая ставка ЦБ.

**Алгоритм встречного предложения:**
Если ML-алгоритм не может одобрить заявленные `request.amount` по базовой ставке каталога (например, из-за превышения долговой нагрузки в 40%), он пытается рассчитать альтернативу в пользу банка:

1. **Корректировка ставки:** Новая ставка рассчитывается как `key_rate_pct + risk_margin` (где маржа риска зависит от скорингового балла, насчитанного линейной моделью).

2. **Снижение лимита:** Модель рассчитывает максимально возможный `amount` при новой (более высокой) ставке так, чтобы ежемесячный платеж уложился в 40% от среднемесячной выручки клиента.

3. Если полученный `amount` больше минимально допустимого лимита продукта, клиенту выдается решение `COUNTEROFFERED`.

## 5. Структура принятия решений (Decision & Offer)

Результат работы ML-алгоритма формирует объект `Decision`:

| Поле | Тип | Описание | 
| ----- | ----- | ----- | 
| `kind` | enum | `APPROVED`, `COUNTEROFFERED`, `DECLINED`, `REQUEST_INFO` | 
| `reason` | string | Человекочитаемая причина (напр., "Запрошенная сумма недоступна, предлагаем альтернативные условия") | 
| `conditions` | object | Сохраненный расчет: `averageMonthlyRevenue`, `totalMonthlyPayment`, `missingFields`, `key_rate_pct` | 
| `alternative_terms` | object | (Только для `COUNTEROFFERED`): `amount`, `termMonths`, `annualRatePct` (пересчитанная с учетом ключевой ставки) | 

При статусе `APPROVED` или после акцепта `COUNTEROFFERED` клиентом, генерируется объект `Offer` с точными утвержденными параметрами, который ведет к подписанию договора (Contract) и выдаче (`Disbursement`).
