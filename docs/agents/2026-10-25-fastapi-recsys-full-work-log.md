Дата отчёта: 25 октября 2026 года. Основные работы: 24–25 октября 2026 года.
Ветка: `fast_api`. Последний коммит реализации перед этим отчётом: `acbbc0b`.

Статус: сервер и дообученная модель реализованы, связка с Java проверена,
модель опубликована на HF и подключена к рабочему Docker-контейнеру.
Экспертная оценка качества и строгая приёмка всего сервера с 6 ГБ RAM остаются

## Запрос, границы и источники

Первоначальная задача — реализовать в `fastapi/` самостоятельный ML-сервис по
`fastapi_recsys_codex_pack_v2.zip`: Java передаёт профиль и допустимые продукты,
FastAPI возвращает смысловой порядок. За основу сборки текстов была выбрана
архивная редакция v2, отличавшаяся от первоначального `info/query_passage_mvp.md`.
Материалы хакатона из `info/` использовались как исходные требования.

В согласованный объём вошли DTO, сборка текстов, encoder, ранжирование, API,
контроль нагрузки, тесты, инфраструктура и передача модели. В ходе обсуждения
добавились Java-адаптер, калибровка, reranker, дообучение и публикация на HF.
Финансовую применимость, условия кредита, скоринг и кредитное решение модель
RecSys не определяет. Реализация SBA-скоринга в других ветках/задачах команды
не является результатом этой работы.

При составлении отчёта прочитаны `AGENTS.md`, общий индекс и существующие отчёты
команды, история Git, текущие конфигурации/код, сохранённые ML-эксперименты и
локальные результаты проверок. При расхождении старого отчёта и последующей
реализации ниже явно указано актуальное состояние.

Ранее пользователь запрещал менять `docs/`, поэтому подробные отчёты этапов
сохранялись в `fastapi/experiments/`. Текущий прямой запрос разрешает новый общий
лог в `docs/agents/` и ссылку в индексе. Исторические отчёты не переписываются.
`draft.ipynb`, секреты, данные рабочей БД и замороженные веса этой задачей
документирования не изменяются. Запрет агента на GitHub push сохраняется.

## Сервер, контракт и сборка текстов

Реализованы строгие Pydantic v2 DTO с `extra=forbid`, enum, ограничениями длины,
уникальностью и проверками security. Повторные product ID, неизвестные коды,
`INELIGIBLE` и условное обеспечение без пояснения отвергаются. Контракт покрывает
шесть семантических полей профиля и двенадцать полей продукта.

Независимые `build_query` и `build_passage` используют русские подписи и порядок
v2, нормализуют Unicode NFC, пробелы, управляющие символы и пунктуацию.
Добавляются E5-префиксы `query:`/`passage:`. Неизвестное значение пропускает
соответствующую фразу, но не делает весь профиль пустым; `null` не превращается
в `NO`. Отрицания и известные ответы об обеспечении сохраняются.

В passage входят назначение, режим использования, сценарий, специализация и
обеспечение. Имя, ID, версия, рекламное название, суммы, сроки и ставки не
используются для смыслового сходства. Свойства продукта не выводятся из названия.
Enum-массивы нормализуются детерминированно; предупреждения Java возвращаются
в исходном порядке без изменения их содержания.

Ранжирование использует нормализованные векторы и scalar product, то есть cosine.
Сортировка выполняется по полной точности, точное равенство разрешается по ID;
оценка округляется до шести знаков только в ответе. Все кандидаты возвращаются
всегда. Пустой список не вызывает encoder. Штрафов за `CONDITIONAL`, процентов
соответствия и скрытых ручных весов признаков не добавлено.

LRU хранит до 512 passage-векторов. Ключ включает текст, модель, revision,
версию passage-шаблона и словаря. Query не кэшируется; версии, eligibility и
предупреждения не берутся из старого запроса вместе с вектором.

## API, ограничения нагрузки и безопасность

| Endpoint | Назначение и доступ |
|---|---|
| `POST /api/v1/recommendations/rank` | Исходный rank-v2; `X-Internal-API-Key`. |
| `POST /api/v1/recommendations/rank-java` | Автоматический Java-обмен; внутренний Bearer key. |
| `GET /api/v1/model-info` | Фактическая модель, revision, шаблоны и порог; внутренний ключ. |
| `GET /health/live` | Проверка процесса без inference. |
| `GET /health/ready` | Готовность ресурсов без повторного inference. |
| `GET /health` | Совместимый alias проверки процесса. |

В production отвергаются пустые и примерные внутренние ключи; сравнение ключей
выполняется безопасно. Тело ограничивается при чтении 512 КиБ, включая передачу
без `Content-Length`. До encoder проверяется длина текста с prefix и special
tokens: более 512 токенов даёт `422 TEXT_TOO_LONG`, без молчаливой обрезки.

Одна модель создаётся в lifespan. Inference выполняется последовательно в одном
выделенном worker thread. Допускается максимум четыре rank-запроса, включая
работающий; ожидание допуска ограничено одной секундой, далее `503 SERVICE_BUSY`
с `Retry-After`. Отмена HTTP-запроса не освобождает слот до завершения потока.
Health остаётся доступным во время inference; shutdown ожидает завершения работы.

Ошибки имеют единый JSON-формат. В них не сериализуются пользовательский input,
ключи и внутренние сведения Pydantic. Технические rank-логи содержат requestId,
время, количество кандидатов/рекомендаций, cache hit/miss и версии, без текстов
профилей и продуктов. Ошибка manifest/identity останавливает startup; fallback
на другую модель не выполняется.

## Совместимость с Java и границы вклада

Изучены текущие `RecsysGateway`, `AutomaticSelection`, `RankingExchange`,
`RankingVocabulary`, `ProductSemantics`, JSON Schema и отчёты backend-команды.
Реализован Python-адаптер к `query-passage-mvp-2` / `synthetic-semantics-1`:
UUID запроса и продуктов, `queryFields`, Java-словарь, семантические карточки,
полные `pendingConditions` с `actual`/`expected` и статусы применимости.
`LOGISTICS` переводится во внутренний `TRANSPORT` для сборки текста.

Ответ содержит ровно четыре metadata-поля Java: `model`, `modelVersion`,
`queryTemplateVersion`, `passageTemplateVersion`. Полный список, productVersion,
eligibility и условия Java сохраняются. Поля анкеты о финансах не добавлялись
в семантический запрос. Java-клиент и основная бизнес-логика создавались командой
backend; в рамках ML-работы также согласовано ограниченное изменение проверки
Java `isRecommended` на непрерывный префикс от 0 до `topK` и его регрессионный тест.

Проверялась реальная цепочка Java HTTP gateway → CPU E5 → Java validation/import
в отдельных временных Compose-проектах с PostgreSQL. Успешны conditional,
unknown_context и logistics (`READY`, по четыре кандидата), empty (`EMPTY`, ноль).
Проверены metadata, исходные условия, idempotent import/retry и отказ `409` при
устаревшей форме. В последнем прогоне с текущим F1-порогом в трёх непустых кейсах
рекомендованы три из четырёх кандидатов. Это конкретные проверки, а не требование
всегда выдавать три. В прямом HF-тесте другие запросы дали 1, 1 и 0 рекомендаций.

Сохранённая Java response schema совпадает с Java-owned схемой в `docs/contracts/`.
Некоторые исторические документы команды ещё описывают ручной обмен и ровно top-3;
текущее поведение проверялось по коду и тестам. Эти документы не переписывались.

## Демо-данные и диагностика маркетплейсного продукта

Первоначальные 40 кейсов — пять базовых ситуаций с восемью вариациями, а не сорок
независимых клиентских исследований. Релевантность задавалась предложенной
синтетической разметкой; модель вычисляла ранжирование, не экспертный эталон.
Для кейсов был сохранён статус `MANUAL_REVIEW_REQUIRED` и предварительный отчёт
HitRate@3=1.0. Такой результат на пяти продуктах не считался доказательством
качества на полном каталоге, отрицаниях и реальных клиентах.

По запросу пользователя выполнен отдельный прогон фактических 15 синтетических
продуктов и восьми сценариев Java. Без подтверждённых меток для него не объявлялись
метрики качества; результаты использовались как диагностика полного ranking.

Для частых маркетплейсных рекомендаций проверены исходные тексты, длины,
нормы, сортировка и контрфактические варианты полей. В 32 коррелированных
вариациях вне маркетплейсной группы продукт был первым 11 раз и в top-3 — 31 раз.
Изменение отрасли и обеспечения переносило существенную часть преимущества;
удаление одной специализации даже увеличивало спорные первые места.

Вывод относился к этому набору: общий эмбеддинг смешивает цель, отрасль,
специализацию и обеспечение; частично заполненные карточки различаются по объёму
сигнала. Принудительный top-3 дополнительно включал далёкие предложения.
Фраза об отсутствии продаж на маркетплейсах не гарантирует логического запрета
специализированного продукта. Искусственные правки карточек не переносились
в рабочий каталог, ручной штраф для маркетплейса не добавлялся. Порог уменьшает
лишние рекомендации, но сам по себе не исправляет неверный порядок.

## Калибровка, независимость наборов и reranker

По запросу пользователя `isRecommended` отделён от полного ranking:
рекомендуются только первые позиции, удовлетворяющие cosine distance-порогу,
не более `topK` и трёх. Если порог не задан, рекомендаций нет; это явно отражается
в metadata основного API. Порог не подбирался по 40 старым или восьми Java-демо.

Созданы 180 calibration и 90 holdout-сценариев с разбиением по семействам, включая
цели, режимы использования, специализацию, отсутствие описания, отрицания,
обеспечение и случаи без релевантных продуктов. Метки `SYNTHETIC_PROPOSED` требуют
экспертной проверки. Исходная E5 получила собственную калибровочную политику.

Затем проверен `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, CPU float32,
revision `1427fd652930e4ba29e8149678df786c240d8825`. Его raw logits не выдавались
за cosine и не внедрялись в API. Сравнивались F1, F0.5, precision при recall ≥0.50,
recall при precision ≥0.80 и минимальном coverage. Невыполнимые ограничения
фиксировались как невыполнимые, без скрытого ослабления.

Старый holdout стал development. До итогового inference подготовлены новые
90 сценариев и зафиксирован основной вариант `e5/f1` по development-протоколу.
На новом test CrossEncoder/F1 дал F1 0.6732 против 0.6601 E5, но development F0.5
и итоговый NDCG@3 не подтвердили устойчивой победы. На 15 кандидатах model-only
Linux benchmark дал p95 около 60 мс для E5 и 953 мс для E5+CrossEncoder.
Reranker оставлен экспериментом, в текущий runtime не включён.

## Дообучение E5 и выбор текущей политики

Созданы train 1500 профилей / 300 семейств, 10610 пар: 2060 positive и 8550
negative. Development — 180 профилей (`holdout` + `reranker-test`), calibration —
180, отдельный `finetune-test` — 90. Код проверяет отсутствие пересечений familyId
и точных query между train/calibration/development/final. Каталог из 15 продуктов
общий: эксперимент проверяет новые запросы к известному каталогу, не новые продукты.

Обучение выполнялось на NVIDIA GeForce RTX 4070 Laptop GPU в отдельном Windows
CUDA-окружении, а production остался CPU-only. Full fine-tuning, не LoRA:
OnlineContrastiveLoss margin 0.5, две эпохи, batch 16, LR 2e-5, weight decay 0.01,
BF16, seed 20261024. Лучший checkpoint — шаг 1328; длительность около 315 секунд,
peak allocated VRAM около 2.39 млрд байт. Отдельный CUDA `uv.lock` сохранён.

По записи обучения development AP изменился с 0.5600 до 0.9777; checkpoint выбран
по development, а не по calibration/final. Первоначально порог дообученной модели
выбирался по calibration F0.5: max distance 0.4941788911819458.
Исторический final90 тогда дал P=96.00%, R=93.02%, F1=0.9449.

После обсуждения recall пользователь попросил применить ранее рассчитанный
calibration F1-вариант. Текущая политика:

```text
min cosine similarity = 0.47622181475162506
max cosine distance   = 0.5237781852483749
```

Критерий — максимум micro F1 на calibration; при равенстве выше precision,
затем меньше distance. Модель и веса при замене порога не менялись. Порог
привязан к artifact SHA, версиям шаблонов, SHA calibration и каталога.

| Повторная диагностика текущего F1-порога | Precision | Recall | F1 | TP / FP / FN |
|---|---:|---:|---:|---:|
| Ранее выделенный finetune-test, 90 | 91.85% | 96.12% | 0.9394 | 124 / 11 / 5 |
| Дополнительные diagnostic-15 | 89.47% | 85.00% | 0.8718 | 17 / 2 / 3 |

Рост recall сопровождается снижением precision и качества отказа: на final90
правильно пустые рекомендации для нерелевантных кейсов изменились с 12/12 до 9/12.
Эти наборы к моменту повторной диагностики уже просматривались. Повторный прогон
не объявлялся новой независимой финальной оценкой. Все метрики остаются
предварительными для синтетической разметки; реальное качество не доказано.

промежуточные training checkpoints не требуются.

Репозиторий сначала был private, позже пользователь сделал его public.
Анонимные `model_info`, скачивание manifest и запрос metadata весов были успешно
проверены с `token=False`; `private=false`, `gated=false`. Записи private в старых
отчётах и информационном поле HF lock отражают прошлое состояние и не включают
требование авторизации в runtime. Для публичной модели HF_TOKEN не обязателен.

## MODEL_PATH, кэш, рабочий Docker и инфраструктура

Источник выбирается одной переменной в `.env`; это альтернативы, не три строки
одновременно:

```dotenv
MODEL_PATH=thedauns/e5-credit-finetune-v1
# MODEL_PATH=C:/models/e5-credit-finetune-v1/final
# MODEL_PATH=/srv/models/e5-credit-finetune-v1/final
# MODEL_PATH=s3://bucket/prefix
```

Короткое известное HF-имя использует SHA из `config/hf-deployment.lock.json`.
Полная форма: `hf://namespace/repo@<40-character-SHA>/model`.
Относительный локальный путь можно начинать с `./`. Старые параметры источника
оставлены совместимыми, но MODEL_PATH имеет приоритет. Файлы другой модели
должны соответствовать lock и manifest; смена адреса не отключает проверку identity.

При прямом Python-запуске читается `fastapi/.env`, в Compose — корневой `.env`;
переменные процесса имеют приоритет. Для private HF доступ передаётся отдельно
через HF_TOKEN; для S3 — AWS credential chain/IAM или отдельные AWS-переменные,
для совместимых сервисов предусмотрен S3_ENDPOINT_URL. Авторизация HF CLI на
Windows сама по себе внутрь Docker не переносится. Внутренний RECSYS_API_KEY
для Java/FastAPI нужен независимо от публичности HF.

S3 поддержан кодом и mocked unit-тестами загрузки, кэша, manifest/checksum,
ошибок и небезопасных путей. Реальный bucket не создавался, данные туда не
отправлялись; реальная S3-интеграция не объявлялась проверенной.

HF скачивается при startup в дисковый кэш, затем проверенные файлы загружаются
в одну модель в RAM. Три различных Java-запроса прошли с запрещённой сетью;
объект модели и адреса тензоров сохранились, constructor/resolver повторно не
вызывались. Новая lifespan с `HF_LOCAL_FILES_ONLY=true` прошла из готового кэша
без внешних соединений. При завершении процесса RAM не сохраняется; после
рестарта веса снова загружаются из дискового кэша.

В Linux HF snapshot может содержать ссылки в blobs. Для строгого самодостаточного
manifest предусмотрена materialization в обычные файлы внутри writable кэша;
выходящие за его пределы ссылки отвергаются. Это отдельно проверено под WSL.

Финальный Compose использует non-root runtime, read-only root и веса,
внутреннюю сеть для Java, исходящую сеть для HF и постоянный named volume
`recsys_model_cache:/model-cache`. ML-порт по умолчанию не опубликован наружу.

На первом настоящем HF-download в read-only контейнере обнаружена недоработка:
отдельный Xet-кэш пытался писать в `/app/.cache`. Ранние Linux smoke с готовым
кэшем этот путь не покрывали. В Dockerfile и Compose закреплены:

```text
HF_CACHE_DIR=/model-cache
HF_HOME=/model-cache/hf-home
HF_XET_CACHE=/model-cache/xet
```

После исправления пересоздан только FastAPI. Десять файлов скачались примерно
за 22 секунды, startup завершился, контейнер стал healthy, RestartCount=0.
В рабочем Uvicorn-процессе `/rank` и `/rank-java` вернули 200 и всех кандидатов;
model-info подтвердил artifact SHA и текущий F1-порог. Полный первый запуск до
healthy занял около минуты, а не четыре секунды сборки image.

Окружение Python 3.11 закреплено настоящим `uv.lock`; runtime PyTorch берётся
из CPU index, CUDA-тренировка имеет отдельное окружение. Экспорт requirements
обновлялся из lock. В CI обычный contracts job работает с fake encoder;
ручные model-package/real-java используют MODEL_PATH, проверку manifest,
настоящий CPU smoke и Docker/Java. Успешный запуск этих GitHub Actions на
удалённом сервере агентом не заявлялся.

В первоначальном коммите v2 готовились также Kubernetes-манифесты: одна реплика,
Recreate, probes, Secret/PVC, memory request 1536 MiB и limit 2 GiB. В текущем
checkout соответствующего `infra/kubernetes/fastapi/deployment.yaml` нет.
Актуальный рабочий запуск проверен в Compose; развёртывание Kubernetes или VPS
в рамках этой работы не выполнялось.

### Бюджет 6 ГБ и обнаруженное ограничение задержки

В последнем замере одновременно работали FastAPI, Java, PostgreSQL, frontend
и pgAdmin. Проверены cold/warm 1, 10 и 100 кандидатов, затем четыре параллельных
запроса со 100 разными passages. Все десять HTTP-запросов успешны.

Максимальная измеренная сумма cgroup memory.current пяти контейнеров —
2767511552 байт: около 2.77 decimal GB / 2.58 GiB, включая charged file cache.
Исторический пик FastAPI — 1773.54 MiB / 1.73 GiB при лимите 2 GiB. Swap у всех
равен нулю, OOM и OOM-kill отсутствуют; backend health/frontend вернули 200.
Docker stats показывал меньшую сумму, так как исключает часть файлового кэша.

Это не строгая приёмка сервера с 6 ГБ: Docker Engine имел 7.37 GiB, только ML
ограничен по памяти, остальные службы без container memory cap. ОС/Docker VM,
сборка образов и конкурентная бизнес-нагрузка на Java/БД в замер не входят.
Фактический ML-сценарий укладывается в бюджет, гарантии всего сервера пока нет.

При четырёх холодных 100-кандидатных запросах завершение заняло 3.66–14.89 с
из-за последовательного inference. Последние два превышают максимальные 10 с
Java-клиента. Это отдельный вопрос пропускной способности/таймаута, не ошибка
RAM; параметры нагрузки и Java timeout этим замером не менялись.
