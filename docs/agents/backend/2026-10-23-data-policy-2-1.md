## Implemented

- FormPolicy: distinct schemas, 19 preliminary / 15 final / exactly 11 shared fields.
  Identity such as taxId is company data, not a questionnaire field. No future debt/overdue
  values are accepted in the preliminary form. Eight selection-only fields remain in a
  separate preliminary context. Provenance stays DECLARED until independently reviewed;
  submit explicitly records client confirmation.
- Eligibility: amount/term/purpose/business kind, geography, sector exclusions, tax regime,
  age/revenue history, MSP, IP age, collateral/guarantor readiness, marketplace/account rules.
  Structured PASS/FAIL/UNKNOWN/REVIEW reasons; aggregate ELIGIBLE/CONDITIONAL/INELIGIBLE.
- SelectionProfiles: immutable runs, catalog snapshots, order by eligibility/product code,
  NULL personal score and personalRatingAvailable=false. No pretend personal recsys.
  Choosing requires current profile version/run; edits clear the choice.
- ApplicationService: create from selected profile/version, project 11 inherited fields,
  accept final-schema additions, preserve separate selection context. Explicit refresh of
  the same selected profile/product in DRAFT/NEEDS_INFO does not overwrite final answers.
  Submission freezes product/context/documents/optional financial evidence and confirmation.
- Payments: exact Decimal annuity for published FIXED/ANNUITY products, known maintenance
  fee and upward cent rounding. Unsupported facility-specific/seasonal schedules return
  REQUEST_INFO/paymentSchedule instead of inventing a formula.
- DemoAssessment: opt-in, synthetic products only, fixed reproducible weights, version
  demo-fixed-weights-1, mode DEMO. No training, randomness or external calls.
- DataPolicy 2.1: full final-data checks, overdue >0.2 blocks any counteroffer, no positive
  new credit when current obligations exhaust the 40% revenue budget. Candidate alternatives
  recompute demo assessment/margin, payment and budget; amount decreases and must be strictly
  above the product minimum, rate increases, term is unchanged. Stable reasonCode values.
- MacroContext: bank-created immutable versions with key rate, source, validity and expiry.
  No automatic CBR fetch and no hardcoded current rate. Test value 10 is explicitly fictitious.
- Counteroffers: separate immutable proposal; Decision.kind COUNTEROFFERED and alternative_terms.
  No Offer until owner accepts exact proposal/hash. Offer/acceptance/state transition are
  atomic, repeated acceptance reuses the Offer. Original revision stays unchanged; final
  contract/disbursement use the accepted alternative amount/rate.
- FinancialEvidence: separate immutable operations, revenue calculation, exclusion of loans
  and internal transfers, no duplicate external IDs, explicit bank review. Unknown categories
  request information. Verified discrepancies go to UNDER_REVIEW with reasons/checks;
  users/bank can inspect operations via authenticated GET.
- Product document requirements include guarantor, collateral and scenario-specific supporting
  documents. Uploaded documents do not become verified automatically. Positive bank commands
  cannot bypass the policy, unavailable assessment or unverified documents.
- Journey exposes current checks and evidence/reasons, only the active decision's offer/proposal,
  plus immutable history, contracts and disbursements.
- DemoScenarios: 8 deterministic business scenarios/companies, seeded for the demo owner,
  exposed to authorized members/bank only; explicitly UI/backend examples, not training data.
- Updated README, backend plan/API, data dictionary, storage contract, Postman guide and
  validation report. User source documents copied without changes.

## Explicit demo choices / limitations

- Fixed weights/threshold/margin are documented in docs/data-dictionary.md and are not
  empirical credit methodology. DEMO_ASSESSMENT_ENABLED must be explicitly true in Compose;
  it is disabled there by default if absent from the environment. .env.example opts in.
- Synthetic counteroffer policy permits amount decrease/rate increase, unchanged term,
  rate cap 100%. This is a versioned synthetic policy description, not a real-bank tariff.
- Any verified exact revenue discrepancy requires review; no unsupported materiality threshold
  was invented. Operation categories must be explicitly supplied and reviewed.
- Key rate must be provided as a valid bank-created server context; sourceCode identifies it.
  No live key rate is fetched or claimed in examples.
- No trained risk/recommendation model, FastAPI integration, LLM assistant or personal ranking.
  FastAPI remains its previous /health scaffold. These are other-team/separate dependencies.
- Non-annuity facility schedules need a separately agreed calculation; current result is REQUEST_INFO.
- Existing submitted legacy data is retained as history; new flows use the new schemas.
- Real signatures and money transfers are not implemented; the route remains a simulation.
