Дата: 2026-10-26. Статус: завершено.

## Запрос и границы

Проверить текущее состояние проекта и поддержку полного пайплайна оформления кредитной заявки; отсутствие настоящей модели кредитного скоринга допускается. Проверка включает код, контракты, клиентский интерфейс, банковские операции, хранение и доступные автоматические проверки. Изменения прикладного поведения не запрошены.

Следуем AGENTS.md: отдельный отчёт, обновление общего индекса, без секретов и персональных данных. Исходное рабочее дерево чистое; HEAD `2e88bd9`.

## Основной вывод

Backend реализует сквозной **демонстрационный** процесс до `DISBURSED`, включая дозапрос, отказ, встречное предложение, акцепт и условный договор. Это подтверждено текущим прогоном тестов с настоящим PostgreSQL. **Сквозной пользовательский процесс через сайт не завершён**: интерфейс заканчивается подачей и просмотром статуса; банковские операции, акцепт и подписание существуют только в API.

Настоящей модели кредитного скоринга нет. E5/FastAPI отвечает за рекомендации продуктов, а не риск кредита. Без обученного скоринга можно демонстрировать весь backend-процесс с включённой фиксированной `DemoAssessment`. Если отключить и её, подходящая заявка возвращается в `NEEDS_INFO` с причиной `ASSESSMENT_UNAVAILABLE` и `missingFields=[scoring]`; ручное одобрение это ограничение не обходит.

Текущая локальная конфигурация дополнительно блокирует обычный запуск Compose: отсутствует обязательный `RECSYS_API_KEY`. На момент первоначальной проверки запущенных Docker-контейнеров не было.

## Основные разрывы и их последствия

### 1. Блокер полного сценария в интерфейсе: действия после подачи

В `frontend/src/components/Applications.tsx` есть submit, редактирование, загрузка документов и обновление статуса. Нет вызовов `offers/accept`, `counteroffers/accept` и `contract/sign`. Тип `Journey` (`frontend/src/types.ts:122`) не описывает offer, counteroffer, contracts или disbursements. При `APPROVED` и `COUNTEROFFERED` пользователь видит статус/причину, но не может продолжить оформление.

API для этих действий уже есть в `CabinetController.java:226` и `ApplicationService.java:995`; точный акцепт альтернативы реализован отдельно. Для завершения сайта нужно показывать сохранённые условия и срок, давать явный акцепт и условное подписание, показывать договор и результат выдачи.

### 2. Блокер самостоятельного рассмотрения: нет банковского UI и автоматического запуска обработки

Подача (`ApplicationService.java:351`) сохраняет ревизию и переводит заявку в `SUBMITTED`. Она не вызывает обработку. Проверки/решение запускаются отдельной банковской командой `POST /bank/applications/{id}/process` либо `decisions`. Планировщика/фонового работника, который подхватывал бы SUBMITTED, в исследованной реализации нет. Само обновление клиентского статуса обработку не запускает.

Банковские очередь, назначение, дозапрос, проверка документов/операций, решение, макроконтекст и выдача доступны через API, но frontend не содержит вызовов `/bank/`. Для полного демонстрационного пути сегодня нужен сотрудник с API/Postman. Требуется либо банковский UI, либо явно согласованная автоматическая оркестрация демонстрации.

### 3. Различать «без обученной модели» и «без любой оценки»

`DemoAssessment` — фиксированная взвешенная формула `demo-fixed-weights-1`, только для синтетических продуктов, без обучения. Для полного демонстрационного backend-пути нужны `DEMO_ASSESSMENT_ENABLED=true` и действующий макроконтекст, созданный банком. Отсутствующий макроконтекст не заполняется автоматически. Неаннуитетный график возвращает `PAYMENT_SCHEDULE_REQUIRED`.

При отключённой DEMO-оценке `DataPolicy.java:182` возвращает `ASSESSMENT_UNAVAILABLE`. `ApplicationService.java:565` не разрешает ручному APPROVED/COUNTEROFFERED обойти результат policy. Поэтому формулировка «полный путь без скоринговой модели» сейчас достижима с DEMO-оценкой, но не с полностью отключённым этапом оценки. Для другого поведения потребуется отдельное изменение контракта принятия решения.

FastAPI подключает маршруты health, model-info, rank и rank-java (`fastapi/app/main.py:63`); отдельного кредитного scoring endpoint и Java-клиента к нему нет. План `docs/credit-scoring-implementation-plan.md` прямо имеет статус плана, а не выполненной интеграции.

### 4. Текущий стенд не запускается стандартной командой

`docker compose config --quiet` завершился с кодом 1: обязательный `RECSYS_API_KEY` не задан. Проверены только признаки наличия конфигурации; секретные значения в отчёт не включались и не менялись.

В текущем `.env` также не задан `MODEL_PATH`, а локальная папка `fastapi/models` отсутствует. Compose по умолчанию использует `/models/e5-credit-finetune-v1/final`. До следующего запуска нужно задать рабочий источник E5 или подготовить локальную модель. Это отдельная модель рекомендаций. Backend в Compose ждёт healthy FastAPI (`compose.yaml:52`), поэтому для стандартного стека её готовность обязательна, несмотря на наличие прикладной обработки недоступности рекомендаций.

В `.env` demo-профиль и DEMO-оценка включены, пароли demo-аккаунтов заданы. Содержимое паролей не проверялось и не приводится. Макроконтекст после запуска создаётся отдельным банковским API-вызовом; его наличие на работающем стенде в этой задаче не проверялось.

### 5. Небольшой дефект отображения документов

После загрузки документа frontend получает новый journey и меняет его состояние (`Applications.tsx:537`), но не обновляет `requirements`. Этот список загружается при открытии/обновлении страницы (`:73`), а сервер при загрузке переводит требование в RECEIVED. До повторного открытия/обновления клиент может одновременно видеть сообщение «документ загружен» и старое «нужен документ». Вывод по коду, отдельно в браузере не воспроизводился.

### 6. Широкий банковский путь из reference ещё не реализован целиком

Новые заявки создаются с `workflow_mode=SIMPLIFIED` (`ApplicationService.java:198`). План проверок при подаче содержит два агрегированных DATA_POLICY gate (`:432`). Состояния VALIDATING/ENRICHING/SCORING проходят последовательно в одном вызове обработки; наличие этих статусов не доказывает работу внешних интеграций.

В прикладном коде не найдены рабочие процессы идентификации/полномочий, отдельных согласий, официальных запросов БКИ/реестров, антифрода/комплаенса, регистрации залога и сопровождения кредита, описанные в `docs/reference/credit-journey.md` и широкой анкете `full-application.md`. Таблицы и SQL-ограничения сами по себе не являются интеграциями. Вход в существующий аккаунт не следует считать внешней идентификацией.

`Documents.contract` создаёт `contract.json` с техническими идентификаторами и `isSimulated=true`; это не полноценный текст кредитного договора. Подписание — подтверждение действия пользователя, выдача — запись в БД без перевода денег. Эти границы соответствуют README и не скрывают настоящие банковские интеграции.

## Ограничения проверки

- Не запускались текущие FastAPI-тесты, настоящая E5 и HTTP/browser acceptance всего стека. На хосте нет подходящего подготовленного ML-окружения и локального checkpoint; ранее выполненные проверки из исторических отчётов здесь не выдаются за новые.
- Сквозные backend-проверки используют Spring MockMvc + настоящий PostgreSQL, а не настоящий браузер. Recsys URL в этих тестах намеренно пустой, DEMO-оценка включена. Это доказывает workflow backend, но не текущую работоспособность Java→реальная E5.
- Docker production-образы в этой задаче не пересобирались и не запускались. Текущие проверки сборки относятся к Java-пакету и frontend; работа ранее существовавших образов не утверждается.
- Внешние банковские/юридические требования не переоценивались; reference использован как внутреннее описание объёма проекта.

## Рекомендуемый порядок завершения MVP

1. Исправить локальную конфигурацию запуска: RECSYS_API_KEY, источник E5; после запуска задать действующий синтетический макроконтекст. Проверить весь стек по HTTP.
2. Добавить банковский экран: очередь → назначение → документы/проверки → process/решение/дозапрос → выдача. До этого API/Postman остаётся обязательной частью демонстрации.
3. Завершить клиентский экран: конкретные недостающие поля/причины, условия решения/контрпредложения, акцепт, условное подписание, договор, результат выдачи. Исправить обновление списка документов.
4. Проверить через интерфейс три сценария: одобрение→выдача; встречное предложение→акцепт→выдача; дозапрос→исправление→повторная подача. Для этих сценариев обученная кредитная модель не обязательна при явно включённой DEMO-оценке.
5. Подключать настоящий кредитный скоринг отдельной задачей по существующему плану, сохраняя нынешние финансовые проверки и историю.
